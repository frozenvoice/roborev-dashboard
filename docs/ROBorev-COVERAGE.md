## v0.64.0 capability notes

- Agent Hook Readiness v1은 strict browser-authorized queryless `GET /api/agent-hooks/readiness`에서 exact v0.64.0의 fixed `agent-hook install --dry-run --agent <codex|claude|grok|droid> --binary <same-exact-binary>` 네 개만 사용한다. Upstream `InstallSpecs`는 plan 뒤 `dryRun`이면 config write 경로 전에 반환하므로 이 exact branch는 write-free다. Missing config는 `would update`라서 `needs-update`이며, process/parser/timeout/truncation failure는 해당 agent만 `unavailable`로 격리한다.
- `agent-hook status`는 `EnsureClient` lifecycle을 통해 daemon을 start/replace할 수 있어 Dashboard가 사용하지 않는다. `agent-hook daemon status`는 stale runtime record cleanup으로 filesystem을 변경할 수 있어 pure read로 취급하지 않는다. `agent-hook dump`는 불필요한 merged config 전체를 출력하므로 사용하지 않는다. Broad install mutation, reset, run과 daemon start/replace/stop은 기존 P row에 그대로 남고 v1 API/CTA에는 없다.
- Readiness DTO는 supported version과 fixed agent/status만 포함한다. Exact config path는 parser 판정 뒤 폐기하고 actual RoboRev binary, HOME/config path, stdout/stderr/config JSON, command/argv, cwd/session/pid/daemon data를 browser에 노출하지 않는다. Browser confirmation은 sanitized semantic argv만 렌더링하고 actual binary/config/HOME path, raw stdout/stderr, actual command construction/argv and daemon lifecycle은 server-only다. Unrelated JSON values는 유지하지만 upstream writer의 formatting을 byte-for-byte 보장하지 않으며 external editor race는 unverified boundary다. Current/unavailable에는 CTA가 없고 Install All, custom Remove/Uninstall, status/reset/daemon/dump/run은 제공하지 않는다. Completion/failure는 readiness를 정확히 한 번 reload하며 locale/repository switch와 polling/SSE는 request를 만들지 않는다.
- Skills Management v2는 exact v0.64.0 custom-path branch의 single-agent mutation만 지원한다: `skills install --path <server-derived-absolute-agent-skills-dir> --agent <codex|claude|grok|droid>`. Plain `skills install` without `--path`와 `skills update`는 여러 agent와 legacy tree를 순회할 수 있으므로 production occurrence가 0이고 계속 P다. Target는 nonempty `CLAUDE_CONFIG_DIR`/`CODEX_HOME`/`GROK_HOME` 또는 Droid `HOME`을 upstream과 동일하게 선택하고, 없으면 `os.UserHomeDir()` fallback을 사용한다. All Dashboard-controlled slow readiness/binding subprocesses complete before the final complete tree/legacy check; external actor가 final filesystem check 뒤 upstream cleanup 전에 legacy path를 만드는 residual race는 upstream `--no-legacy-cleanup` 없이는 제거할 수 없고 filesystem atomicity도 보장되지 않는다.

## Repositories v3C safe repository merge checkpoint

The v3C contract is a narrow duplicate-recovery operation, not a generic merge/delete tool. Exact upstream v0.64.0 exposes no daemon merge route; `repo merge --yes <source> <target>` is the only mutation transport. Upstream resolves both arguments path-first with exact name fallback, then `MergeRepos` consolidates source commits, review jobs and agent-hook snoozes in a transaction, deletes the source row, and preserves target name/path. It does not move filesystem/Git state, mutate Dashboard Registry, or return a machine-readable receipt.

Dashboard eligibility requires one fresh stale source row that is Dashboard-unregistered, `Lstat`-absent and has `jobCount > 0`, plus one target selected by opaque Dashboard repository identity that is freshly registered, canonicalized and also exactly one RoboRev inventory row. Source/target counts, names/paths, fallback keys, command and runtime binding are token-bound; count drift is a 409 and does not launch a process. Source queued/running safety is fail-closed: a bounded typed stream of parent jobs is reconciled with panel summaries and the source inventory represented-count; incomplete coverage, malformed/count-mismatched evidence, panel members not represented by parent summaries, or any active source row rejects the operation. Target inactivity is not a required policy condition because upstream merge leaves target-owned jobs untouched.

Confirm uses the existing shared two-resource repository lease with a peek → release store lock → acquire source/target Gate → release Gate lock → claim token order. Gate busy preserves the token. The one shell-free process uses `repo merge --yes` with exact source/target paths and empty CWD. Once started, only one authoritative readback can produce `merged`: source absent, target unique, target name/path preserved and target job count at least `S + T`. All other started outcomes are `unverified`, with no retry or rollback. Delete remains unsupported; Registry, selection, registration/switch, filesystem and Git semantics remain unchanged.

## CI Workflow Preview v1 checkpoint

The `init` rows above are intentionally split. Root `roborev init` remains P/planned and is not a B capability because its exact v0.64.0 implementation can create the global config/data directory, optionally write repository `.roborev.toml`, update snapshot `.gitignore`, set `core.hooksPath`, create hook directories, install `post-commit`/`post-rewrite` hooks, start the daemon and register the repository. Its production occurrence is 0. The `init gh-action` child is a separate B read/generation surface; Dashboard never treats root initialization as a harmless precursor.

Upstream `init gh-action` calls `LoadGlobal` and `LoadRepoConfig` but ignores their errors, allowing fallback. Dashboard adds a safe typed config preflight using normal upstream resolution and fails closed for malformed/invalid config without exposing config content or implementing a broad second parser. Exact generation uses a fresh canonical selected registered repository cwd and only `init gh-action --output <server-private-temp>\roborev.yml --roborev-version 0.64.0`. `--agent`, `--force`, custom output, custom version, shell invocation and browser-provided argv are unsupported. A fresh exact binary/version/file binding is checked before generation and again afterward; drift is a fail-closed error.

The output lives in an unpredictable server-owned OS temp directory outside the repository. It must be absent before launch and is cleaned on success, error and cancellation. The post-process read is limited to 256 KiB and requires stable regular non-symlink/non-reparse file identity, valid UTF-8 and no NUL/control characters. The returned workflow is the exact generated bytes and SHA-256. No repository write or directory/config/hook/Git mutation, daemon start, registration, storage DB access, LLM call or network request occurs. Raw stdout/stderr, path, executable/binary, cwd, environment, process details and upstream errors remain server-side; only generated secret references are allowed and actual secret values are never read or returned.

The UI is an Agents & Setup Generate-only card near repository-scoped Git Hooks. Initial entry makes no request; one POST is allowed per Generate click with a double-click guard. Repository switches clear state, do not auto-fetch and discard stale responses; locale changes add no request and may preserve the result; unmount ignores late completion. The card shows fixed target `.github/workflows/roborev.yml`, version `v0.64.0`, plain-text YAML, Copy and the supply-chain warning that the RoboRev pin does not pin every agent installer (`npm @latest`, unpinned Droid `pip`, and Grok `curl -fsSL https://x.ai/cli/install.sh | bash`). `targetStatus` is omitted in v1, so existing repository target state is not read. There is no write CTA, polling or SSE. A later checkpoint must separately design and authorize actual repository writing with target safety/readback; it is not part of this B surface.

The final pre-launch ordering keeps Skills Readiness/Management ahead of any future CI write checkpoint. Review Export remains **BLOCKED** on exact v0.64.0. Tests use deterministic fakes only; no real `roborev init`, `init gh-action`, daemon, LLM or external review job is used.

All Dashboard-controlled config validation and exact binary binding subprocesses complete before the final complete server-owned temp-root/output guard. Immediately before generation, the guard recaptures the temp-root identity and path chain, proves the exact output is absent, and verifies the output's direct-parent identity. A guard failure is sanitized and launches no generation; cleanup remains limited to the validated private temp child. After a successful guard, no Dashboard-controlled operation, subprocess or slow probe occurs before the exact `init gh-action` process launch.

This is not a perfect atomicity guarantee: exact upstream `WriteWorkflow` accepts a pathname, not an already-open safe handle. An external same-user actor can still change the filesystem between the final guard and upstream open/write, so that residual race remains outside Dashboard control and is explicitly not claimed away.
