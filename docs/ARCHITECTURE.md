# Architecture

## 목표와 경계

Dashboard는 React SPA와 Go localhost server로 구성된다. Go server가 repository registry, Git adapter, RoboRev capability layer, typed command builder와 bounded process runner를 소유한다. Browser는 RoboRev daemon이나 OS process를 직접 호출하지 않는다.

```text
Browser (React)
  -> same-origin JSON API + CSRF
Go localhost server
  -> Repository registry -> Git executable + args
  -> RoboRev service
       -> stable JSON CLI (version/show/prompt/log and typed mutations)
       -> version-gated daemon HTTP API (metadata list/enqueue/rerun/panel members/health)
       -> typed CLI mutations (comment/close/cancel)
RoboRev daemon -> RoboRev-owned storage
```

## 주요 선택

### 단일 실행 파일

Vite production output을 `internal/webui/dist`에 생성하고 Go `embed`로 포함한다. 최종 사용자는 Node나 Go 없이 `roborev-dashboard.exe` 하나만 실행한다. 개발 스크립트는 frontend build 후 Go build 순서를 보장한다. `scripts/install.ps1` 소스 bootstrap은 이 runtime 경계와 분리되어 개발 도구만 준비하며 RoboRev를 설치하거나 실행하지 않는다. Dashboard의 RoboRev runtime onboarding은 Go backend가 소유하는 별도 capability다.

### RoboRev runtime 설치 신뢰 경계

`internal/roborevcompat`의 immutable manifest가 Dashboard가 완전히 지원하는 RoboRev release의 version, Windows/architecture, 공식 GitHub asset URL, exact compressed size, SHA-256, archive entry와 managed user target을 한 곳에서 정의한다. installer와 capability layer는 같은 정책을 사용한다. 이번 checkpoint의 권장 버전은 v0.64.0이며 newer/latest를 원격 metadata만 보고 자동 선택하지 않는다. 이미 발견된 supported binary는 존중하고 newer, unknown, broken 또는 policy-blocked binary를 자동 downgrade하거나 덮어쓰지 않는다. explicit `--roborev` override가 있으면 자동 설치를 제공하지 않는다.

Browser는 URL, version, digest, executable 또는 target을 설치 API에 전달하지 않는다. strict-empty same-origin/CSRF mutation이 설치를 시작하면 backend는 pinned HTTPS URL만 요청하고 redirect의 scheme, host, port와 횟수를 allowlist로 제한한다. response는 exact size보다 한 byte 큰 상한으로 streaming 검증하며 pinned SHA-256이 맞아야 다음 단계로 이동한다. 오류 응답 본문이나 signed redirect query는 상태와 log에 포함하지 않는다.

ZIP은 전체를 install directory에 풀지 않는다. root의 exact `roborev.exe` 하나만 허용하고 absolute/traversal/nested path, directory, symlink와 non-regular entry를 거부하며 compressed/extracted 크기를 제한한다. target directory component의 reparse point를 거부하고 같은 directory의 unique staging file을 flush한 뒤 no-replace publish한다. 기존 target은 성공·실패·경쟁 조건 모두에서 삭제하거나 교체하지 않으며 partial target과 알려진 temporary artifact만 정리한다.

설치된 후보는 bounded `version --json`의 exact product name과 canonical compatible version을 통과해야 한다. 그 뒤에만 `roborev.Client`의 mutex-protected generation binding을 atomic하게 교체하고 version/error cache를 새 generation으로 전환한다. 진행 중 command는 시작 시 얻은 immutable binary snapshot을 사용하며 이전 generation의 늦은 probe가 새 cache를 오염시키지 못한다. Dashboard 동작에는 absolute executable을 사용하므로 PATH를 변경하지 않는다.

setup은 process-scoped background state machine으로 checking, downloading, verifying, extracting, installing, binding, daemon start/health와 terminal ready/failed/blocked/unsupported 상태를 typed API로 제공한다. 전역 operation gate는 setup을 exclusive로, 일반 RoboRev mutation과 Panel Refine 전체 run을 shared lease로 취급해 binary rebind와 mutation이 겹치지 않게 하며 충돌은 기다리지 않고 409로 반환한다. daemon reachability와 semantic health를 구분한다. browser-facing `Installation.Status.running`과 setup의 `State.DaemonRunning`은 valid health endpoint가 응답하는 reachability를 나타내므로 `healthy:false`에도 true인 반면, setup ready는 typed probe가 Online, condition이 Healthy이고 canonical daemon version이 installed supported CLI와 exact 일치할 때만 허용한다. idle refresh는 concrete Offline을 기존 installed/stopped ready 상태로 유지하지만 Invalid/Unknown, Online/Unhealthy와 missing·malformed·mismatched daemon version은 retryable daemon failure로 fail closed한다. reachable non-ready Retry는 setup gate 아래 bounded health-only probe만 수행하고 download, rebind, daemon start/restart를 하지 않으며, Offline만 기존 Start daemon recovery를 사용한다. request-scoped refresh는 monotonic generation으로 소유권을 정해 canceled/stale probe를 publish하지 않고 setup operation 수락과 shutdown이 pending refresh를 무효화한다. 검증된 설치는 보존하며 daemon retry에서 재다운로드하지 않는다.

Windows가 exact policy error code로 실행을 거부하면 설치를 ready로 표시하지 않고 `blocked`로 분류한다. Dashboard는 target, requested version과 pinned digest를 계속 표시하지만 Smart App Control/WDAC, registry, Defender 설정을 변경하거나 `Unblock-File` 같은 우회를 실행하지 않는다. generic permission failure는 policy block으로 가장하지 않는다. runtime onboarding은 `roborev init`, Git hook, AI agent 설치·검사, credential 저장과 update를 수행하지 않는다.

### Agent detection과 quota 경계

Agent 목록은 exact v0.64.0 compatibility descriptor와 bounded config reader가 제공하는 safe subset으로 구성한다. global command override와 global/local `[review.subagents]` whole-entry merge를 적용하되 alias, canonical agent, model, reasoning과 resolved command만 반환하고 instructions, provider credential, API key, raw TOML과 dynamic ACP command/args는 읽어 내보내지 않는다. 자동 detection은 regular executable lookup만 사용하며 Cursor의 ambiguous `agent` command에 한해 upstream과 같은 `--version`/`-v` bounded identity probe를 수행한다. probe는 임시 working directory, nil stdin, 짧은 timeout/WaitDelay, bounded combined output과 forge credential/preload hook이 제거된 환경을 사용한다. timeout, empty/crashed/oversized output 또는 Grok identity는 Cursor로 인정하지 않는다.

`Detected`는 executable/config presence이고 `Checked`는 실제 smoke request 성공이다. `GET /api/agents`와 background refresh는 `check-agents` 또는 Agent.Review를 호출하지 않는다. 사용자가 canonical allowlist의 agent 하나를 confirmation한 `POST /api/agents/check`만 fixed `check-agents --agent <canonical> --timeout 60` argv를 request context에서 실행한다. CLI 내부 timeout보다 긴 bounded outer timeout을 두고 v0.64.0의 bounded single-agent output만 최소 parser로 분류하며 결과는 process memory에만 둔다. browser disconnect cancellation은 failure가 아니라 canceled/not-completed다. 설치되지 않았거나 exact v0.64.0이 아닌 runtime에서는 discovery/check를 fail closed해 다른 agent contract를 추측하지 않는다.

Agent health check는 요청이 확인한 selected repository에 전용 read lease를 잡고 single authoritative discovery와 quota-bearing dispatch가 끝날 때까지 유지한다. repository selection commit만 같은 lease의 writer로 직렬화하며 Add, panel preference와 일반 registry read는 막지 않는다. Frontend는 repository identity 변경 epoch와 same-repository `GET /api/agents` request generation을 분리해 단순 refresh가 승인된 check completion을 무효화하지 않게 하고, 실제 repository 변경 또는 다른 scope 응답은 stale health reload와 toast를 거부한다.

### Runtime control lifecycle

Queue state는 prompt/log를 포함하지 않는 official v0.64.0 daemon `GET /api/status`의 typed bounded `queue_paused` 필드에서 읽는다. Pause/Resume은 이미 healthy한 daemon에 `POST /api/queue/pause` 또는 `/api/queue/unpause`를 보내고 exact boolean response를 검증한다. CLI `pause`가 daemon을 암묵적으로 시작하는 경로와 RoboRev DB 직접 읽기는 사용하지 않는다. Pause 중에도 running job은 계속되고 새 queued job만 시작하지 않는다.

Daemon Start/Stop/Restart는 typed `daemon start|stop|restart` argv만 사용하며 확인 UI에는 backend가 제공한 executable과 exact argv만 표시한다. Stop/Restart는 acceptance 뒤 request context와 분리된 process-owned manager가 bounded health/offline verification까지 소유하며, Dashboard shutdown은 active context를 cancel하고 worker와 gate release를 기다린다. restart는 upstream command 하나를 사용해 daemon이 이미 stopped인 경우 start하는 semantics를 보존한다. Stop verification은 transport-level 연결 불가만 offline 증거로 인정하고, reachable HTTP 오류·malformed/oversized/unhealthy health 응답은 실패로 유지한다. 실제 v0.64.0 runtime health envelope의 `$schema`는 optional이며, missing 또는 임의 JSON string을 허용하고 present null/non-string을 거부한다. `DisallowUnknownFields`를 유지해 다른 contract drift도 거부한다. CLI 성공 뒤 health가 기대 상태와 다르면 성공으로 표시하지 않는다. exact v0.64.0 이외에서는 status discovery를 포함한 runtime control 계약을 fail closed한다.

전역 operation gate의 runtime-control lease는 setup, Panel Refine, ordinary mutation과 다른 runtime control 모두와 fail-fast 409로 충돌한다. setup도 runtime control을, mutation/refine도 active runtime control을 거부한다. Queue Pause/Resume은 짧은 runtime-control lease를, daemon lifecycle은 terminal success/failure/cancel까지 유지되는 lease를 사용한다. 따라서 active Panel Refine 중 queue pause나 daemon restart가 workflow를 중간에 stall시키지 않는다.

### Runtime Diagnostics v1

Runtime Diagnostics는 global daemon 상태를 읽는 strict browser-authorized queryless `GET /api/runtime/diagnostics`다. `repositoryIdentity`를 받지 않으며 repository registry, Git identity, operation gate와 무관하다. authorization과 empty-query 검증(`RawQuery`가 있으면 400)은 service/daemon read보다 먼저 수행한다. endpoint handler가 exact supported CLI와 daemon version이 모두 v0.64.0으로 일치하는지 확인하는 동작 gate를 적용하며, 별도의 bootstrap capability flag를 만들지 않는다. daemon이 already-running일 때만 기존 binding을 통해 `/api/health`를 먼저, `/api/status`를 다음으로 한 번씩 읽는다. offline에서는 daemon을 시작·재시작하지 않고 typed unavailable을 반환한다.

두 daemon response는 각각 256 KiB 상한의 `application/json` UTF-8 body로 bounded read하고, exactly one JSON value와 strict typed parser를 적용한다. 기존 client를 shallow-copy해 redirect를 비활성화하며, non-200 response는 body를 읽지 않고 거부한다. required fields, known nonnegative counters와 worker의 의미상 타당성(예: active가 max를 초과하지 않음)을 검증하며 missing, negative, nonsensical, unknown 또는 trailing value는 fail closed한다. 유효한 `healthy:false` health response는 transport failure가 아니므로 정상적인 degraded diagnostics DTO로 반환하고, malformed/oversized/contract-invalid health는 거부한다. Browser DTO는 Dashboard-owned daemon version/running/uptime, worker active/max, queue paused/processing/queued/running, completed/failed/skipped counters와 health/component state 및 제공되는 recent error count만 포함한다. upstream status/health raw JSON, machine/network identity, filesystem paths, free-form messages와 recent-error payload는 전달하지 않는다.

이 GET은 read-only이며 operation gate, lifecycle manager, queue control, repository lease, background polling을 획득하거나 시작하지 않는다. 기존 `/api/runtime`는 version/health TTL polling과 runtime-control lifecycle의 별도 surface로 유지하며 Diagnostics read와 결합하지 않는다. Frontend는 최초 mount에서 요청하지 않고 사용자가 Diagnostics를 명시적으로 처음 열 때만 한 번 요청한다. collapse/reopen은 성공 state를 cache하고, Refresh/Retry만 각각 정확히 하나의 fresh request를 시작한다. 각 request는 `AbortController`와 generation/stale guard로 unmount, superseded refresh와 late response를 차단한다. locale 전환은 현재 DTO와 collapsed/open/error state를 보존하며 fetch를 시작하지 않는다.

### Agent Hook Readiness v1

Agent Hook Readiness는 global read-only `GET /api/agent-hooks/readiness`다. strict browser read authorization과 empty `RawQuery` 검증을 service 호출보다 먼저 수행하며 repository identity, path, scope, timeout, binary, config 또는 argv를 받지 않는다. Backend는 매 요청에 Dashboard-owned RoboRev executable의 canonical regular-file identity와 exact v0.64.0 version을 fresh하게 확인한다. 그 한 binding으로 고정 allowlist `codex`, `claude`, `grok`, `droid` 각각에 shell 없이 `agent-hook install --dry-run --agent <agent> --binary <same-exact-binary>`만 실행하고, probe 뒤 같은 binding을 다시 확인한다. Browser에는 fixed order의 agent key와 `current`, `needs-update`, `unavailable` status, supported version만 반환한다.

Exact v0.64.0에서 `InstallSpecs`는 config를 read/plan한 뒤 `dryRun`이면 실제 directory/temp-file/rename write보다 먼저 반환한다. Readiness는 이 source-proven write-free branch만 사용한다. 반대로 `agent-hook status`는 `EnsureClient`를 통해 daemon을 start/replace할 수 있고, `agent-hook daemon status`는 stale runtime record를 삭제할 수 있으며, `agent-hook dump`는 merged config 전체를 출력하므로 모두 사용하지 않는다. `reset`, `run`, daemon lifecycle과 install mutation도 API/CTA에 없다. Per-agent subprocess는 fixed timeout, separate 64 KiB stdout/stderr bounds, nil stdin과 minimal environment를 사용한다. Windows runtime 환경 외에는 exact config resolver에 필요한 `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `GROK_HOME`, `HOME`, `USERPROFILE`만 전달하며 `GIT_*`, credential, unrelated home/location 변수와 `ROBOREV_*`를 상속하지 않는다.

Parser는 예상 display name의 exact one-line `would update ... in <path>` 또는 `... already installed in <path>`만 받아들인다. Nonzero exit, timeout, truncation, stderr, invalid UTF-8, empty path, extra line/trailing data와 contract drift는 해당 agent만 `unavailable`로 격리하고 다른 agent 결과는 보존한다. Config path는 판정 직후 버리며 actual executable, home/config path, raw stdout/stderr/config, command/argv, cwd/session/pid/daemon data와 upstream error를 DTO나 browser log에 넣지 않는다. Binding/version failure 또는 probe 전후 identity drift만 global failure다. Daemon online 여부, Registry, Git adapter, operation Gate, repository lease, polling/SSE와 무관하다.

Agents & Setup의 compact card는 surface 최초 진입에서 전역 resource를 한 번 읽고 React StrictMode remount와 repository-key remount가 같은 in-flight/settled result를 공유한다. 명시적 Refresh만 fresh GET 하나를 시작하며 더 새 refresh의 generation이 늦은 응답을 폐기한다. Locale 또는 repository switch는 refetch하지 않고 timer polling과 SSE를 사용하지 않는다. v1 card의 유일한 control은 Refresh이며 Install, Update, Reset 또는 daemon control은 제공하지 않는다.

### Agent Hook Management v2

Agent Hook Management v2는 위 readiness DTO의 `needs-update`인 단일 agent에 대해서만 explicit Install / Update를 제공한다. `current`와 `unavailable` row에는 CTA가 없고, all-agent install/update, custom Remove/Uninstall, reset, daemon, dump, run surface는 제공하지 않는다. readiness의 `B` 계약은 유지되며, 단일-agent install/update만 새 `B` capability다. all-agent operation은 `P`/unsupported이고 status/reset/daemon/dump/run도 `P`다. upstream v0.64.0에 uninstall contract가 없으므로 custom Remove/Uninstall도 없다.

Exact v0.64.0 `InstallSpecs`/`PlanSpecs`는 대상 event/matcher의 RoboRev command hook을 install/update하고 stale RoboRev binary runner를 교체하며 duplicate RoboRev hook을 collapse할 수 있다. Unrelated top-level values와 unrelated hooks는 semantic하게 유지하며 plain Codex/Claude, Droid-specific, Grok-specific runner를 서로 구별한다. 전체 config는 JSON decode/encode될 수 있어 whitespace, key order 등 byte-for-byte formatting 보존은 계약이 아니다. Droid의 install default scope도 exact source에서 `user`이므로 Dashboard는 browser scope나 custom config flag 없이 다른 agent와 같은 single-agent argv를 사용한다.

Preview는 strict exact-body `POST /api/agent-hooks/preview` `{agent}` 하나뿐이며, backend가 fresh exact v0.64.0 binding, selected `needs-update` readiness와 bounded dry-run preflight를 확인한 뒤 config safety snapshot에 묶인 opaque short-lived token을 발급한다. Browser에는 exact sanitized semantic command shape `roborev agent-hook install --agent <allowlisted> --binary <current-v0.64.0-binary>`만 반환한다. Actual executable/binary path, HOME/config path, cwd, environment, raw stdout/stderr, actual argv and process details remain server-side; frontend normalizers reject private paths, raw fields, unknown keys and semantic command drift.

Confirmation 이후에만 strict `{token}` `POST /api/agent-hooks/execute`가 한 번 실행된다. Execute는 token, current binding/version과 canonical config path의 existence/fingerprint/file identity safety snapshot을 fresh하게 재검증하고 Dashboard global operation Gate를 사용해 one-shot typed process를 시작한다. 같은 agent의 readiness dry-run은 Gate 안에서 actual install 직전과 detached completion readback에서 각각 bounded하게 다시 수행되며, preview token이나 browser semantic command는 execution authority가 아니다. API는 `verified-success` 또는 `failed-unverified` typed receipt만 반환하고 raw process output이나 path를 반환하지 않는다. 외부 editor/config writer race는 이 Gate/snapshot 경계 밖이며, JSON은 byte-for-byte 보존을 보장하지 않는다. Daemon lifecycle을 시작·중지·재시작하지 않고, completion/failure 뒤 readiness를 정확히 한 번 fresh reload한다. UI는 click에서 preview만 요청하고 confirmation에서 execute만 요청하며, locale/repository switch는 추가 요청을 만들지 않고 polling/SSE도 사용하지 않는다.

### Git Hook Status v1

Git Hook Status v1은 선택된 Dashboard registered repository 하나의 RoboRev Git automation hook만 읽는 repository-scoped `GET /api/repositories/hooks?repositoryIdentity=<opaque>`다. 요청은 strict browser authorization, 정확히 하나의 `repositoryIdentity` query 검증, `Registry.ResolveIdentity`, fresh `Registry.Inspect` 순서를 지킨 뒤 exact supported RoboRev v0.64.0 version gate를 통과해야 한다. version이 missing, unsupported 또는 mismatch이면 `current`를 주장하지 않고 unknown/unavailable로 fail closed한다. browser는 path, repository name, hook name 또는 filename을 authority로 보낼 수 없다.

Version gate 뒤의 Git/hooks adapter는 typed Git subprocess와 sanitized path resolution으로 Git의 `core.hooksPath`, worktree의 `.git` file layout, absolute/relative hooks path semantics를 처리한다. backend가 정한 고정 파일 `post-commit`과 `post-rewrite`만 regular-file/reparse-point safety 검사를 거쳐 각각 최대 256 KiB까지 bounded read한다. ENOENT만 실제 missing/not-installed의 근거로 사용하고, path resolution, permission, malformed object, oversized file과 그 밖의 모든 inspection/read 오류는 unknown/unavailable로 남긴다.

v0.64.0의 marker는 case-sensitive exact string인 `post-commit hook v4`와 `post-rewrite hook v2`다. RoboRev token 탐지는 case-insensitive이며 기존 사용자 shell hook 안에 RoboRev snippet이 embedded된 경우도 standalone file equality가 아니라 같은 규칙으로 판정한다. post-commit은 RoboRev token이 없으면 `not-installed`, token과 현재 marker가 있으면 `current`, token은 있으나 marker가 없으면 `outdated`다. post-rewrite도 고정 파일을 독립적으로 판정하며, post-commit이 RoboRev-installed일 때 RoboRev token이 없는 rewrite는 `missing`으로 표시한다. 두 hook이 모두 없거나 unrelated이면 `not-installed`로 두고, post-commit이 없더라도 rewrite의 positive `current`/`outdated` 사실은 유지한다. Browser에는 typed status/summary만 반환하며 hook contents, absolute hook path, RoboRev binary path, arbitrary Git config 또는 embedded command를 노출하지 않는다.

이 read는 hook/config/repository/daemon을 변경하지 않고 `roborev status`, `install-hook`, `uninstall-hook` 또는 `init`을 호출하지 않는다. daemon이 offline이어도 Git hook filesystem status는 독립적으로 조회할 수 있으며 daemon start/restart는 없다. UI는 새 sidebar page가 아닌 Agents & Setup card에 `Ready`, `Needs attention`, `Not installed`, `Unavailable`과 hook별 status를 표시한다. 최초 surface 진입, repository switch와 명시적 Refresh만 각각 fresh GET을 허용하고 generation/abort stale guard를 사용한다. locale 전환은 fetch하지 않으며 timer polling과 Reviews SSE 결합은 없다. v1에는 Install, Repair, Remove mutation CTA가 없다. `agent-hook` install/status/daemon/harness는 이 Git `post-commit`/`post-rewrite` surface와 별개다.

### Git Hook Management v2

Git Hook Management v2는 기존 read-only 카드에 선택된 registered repository 하나의 고정 `post-commit`/`post-rewrite` RoboRev automation hook만 관리하는 명시적 Install, Repair, Remove를 추가한다. Backend는 exact v0.64.0과 현재 Dashboard-owned executable을 매 preview/execute에서 fresh하게 검증하며 browser가 repository path, binary, argv 또는 hook filename을 제출하게 하지 않는다. 실행 transport는 shell 없이 각각 `install-hook --binary <same-binary>`, `install-hook repair --binary <same-binary>`, `uninstall-hook` argument array만 허용하고 `--force`, `--registered`, `init`, `agent-hook`와 generic command endpoint를 제공하지 않는다. Actual executable/binary path와 binding은 server-side token과 execute 재검증에만 남긴다. Browser confirmation에는 `roborev`와 allowlisted `<current-v0.64.0-binary>` placeholder를 포함한 sanitized semantic command shape만 표시하며, preview는 execution authority가 아니다.

Mutation preflight는 v1의 bounded regular-file/reparse-safe reader를 재사용하지만 broad `roborev` token을 authorization으로 사용하지 않는다. Trimmed case-insensitive `# roborev <fixed-name> hook...` ownership marker, exact current v4/v2 marker와 exact Go-quoted `ROBOREV=<binary>` binding을 server-side에서 구분한다. Non-force Install은 absent 또는 unrelated POSIX shell hook을 생성/병합하고, completion 과정에서 함께 있는 managed current/outdated/stale companion은 upstream semantics대로 no-op 또는 upgrade할 수 있다. 모든 경우 user shell content는 generated block 밖의 residual fingerprint로 보존을 검증한다. Unmanaged non-shell과 marker 없는 ambiguous RoboRev-like content는 Install을 막는다. Repair는 marker-bearing outdated/stale-binary hook만 대상으로 하며 exact upstream처럼 missing companion hook을 생성하지 않는다. Remove는 exact managed block만 제거하고 standalone generated file은 남은 user content가 없을 때만 없어질 수 있다.

Git adapter는 fresh effective hooks path, Git dir/common dir와 effective `core.hooksPath`를 같은 sanitized environment에서 read-only로 해석한다. Canonical hooks directory가 Git dir 또는 common dir 내부이고 기존 path component에 symlink/reparse ambiguity가 없음을 증명할 때만 mutation한다. Tracked worktree/custom external/shared hooks directory는 차단한다. Install이 relative non-tilde `core.hooksPath`를 upstream `EnsureAbsoluteHooksPath`로 local absolute 값에 normalize할 상황도 차단하며 Dashboard는 별도 Git config mutation을 하지 않는다. Repair와 Remove는 이 config normalization command를 호출하지 않는다.

`POST /api/repositories/hooks/preview`는 strict browser mutation authorization/CSRF와 exact body 뒤 fresh repository, binary, layout, safety와 두 fixed file fingerprint를 opaque short-lived single-use token에 bind한다. `POST /api/repositories/hooks/execute`는 token을 먼저 consume하고 selected identity/canonical root/binary generation/layout/config/fingerprint/eligibility를 다시 검사한 뒤 shared operation Gate와 selected-repository lease 아래 typed CLI를 정확히 한 번 시도한다. Preview 뒤 drift나 busy Gate는 409이며 CLI는 실행되지 않는다. Dashboard Gate는 Dashboard 내부 operation만 직렬화하고 외부 editor/Git/RoboRev와 filesystem transaction을 보장하지 않는다.

CLI가 시작되었거나 error를 반환했어도 bounded fresh readback을 항상 수행한다. Readback postcondition이 완전히 충족되면 `verified-success`, action별 기대 진전과 해당 hook의 exact residual 보존이 일부만 증명되면 `partial`, 안전한 readback이나 기대 effect를 증명하지 못하면 `failed-unverified`다. 단순한 unrelated byte 변화나 user residual 변경은 partial 성공으로 간주하지 않는다. Install은 두 hook의 current marker/binary와 기존 residual 보존, Repair는 preview 당시 marker-bearing hook의 current marker/binary와 residual 보존, Remove는 managed block 부재와 exact residual/absence를 요구한다. 자동 retry와 rollback은 없다. UI는 backend availability만 authority로 CTA를 표시하고 click은 preview만 열며 explicit confirmation 뒤에만 execute한다. 완료 뒤 v1 status와 management preflight를 각각 한 번 fresh reload하고 locale 전환은 network request를 만들지 않으며 timer polling은 없다.

### Review Export v1 — v0.64 repository-isolation blocked (2026-08-25)

Review Export v1은 exact RoboRev v0.64.0에서 **BLOCKED**다. 기존 flow는 strict browser authorization, opaque Registry identity, fresh Git root inspection과 `/api/repos` inventory에서 selected `root_path`의 effective export filter를 확인한 뒤 `GET /api/export/reviews?repo=<identifier>`를 호출했다. 그러나 이 검사는 selected canonical root와 실제 export query를 원자적으로 묶지 않는다.

Exact v0.64.0 upstream audit 결과 `ExportReviewsInput`의 repository selectors는 `repo`와 `project`뿐이다. `repo`는 storage query의 `COALESCE(NULLIF(TRIM(identity), ''), name)` filter이고 `project`는 project name filter다. `root_path`는 inventory에서 UNIQUE이지만 export-selectable selector가 아니며, `repos.identity`는 의도적으로 non-unique다. name과 `(effective repo, project)` pair에도 distinct repository rows 사이의 uniqueness invariant가 없다. `/api/repos`와 `/api/repos/resolve`는 export와 별개의 non-atomic requests이고, `storage.ExportReviews`는 앞선 inventory/root resolution에 bound된 transaction 없이 filter query를 직접 실행한다. Export response에는 `repo`, `project`, `database_id`가 있을 뿐 `root_path`, `repo_id` 또는 immutable repository UUID가 없어 selected root를 cross-check할 수 없다.

따라서 inventory authorization 뒤 외부 RoboRev producer, sync 또는 repository mutation이 foreign row에 같은 effective filter를 부여하면 selected A와 foreign B의 metadata가 같은 `row.repo` 값으로 export될 수 있다. before/after inventory read, Dashboard Gate/lease, `row.repo == identifier` 재검증과 `project == name` 검증은 이 query-time race를 원자적으로 해결하지 못한다. v0.64.0에는 `root_path → exact repository row → export`를 하나의 request/transaction으로 묶는 contract가 없으므로 Dashboard가 selected registered canonical root-only invariant를 완전히 보장할 수 없다.

보안 계약을 낮춰 best-effort export로 남기지 않는다. `/api/exports/reviews`는 strict browser authorization, exact single nonblank `repositoryIdentity` query validation, opaque Registry resolve와 fresh Git inspection을 순서대로 보존한 뒤 `501 phase=review-export-repository-isolation-blocked` tombstone을 반환한다. 이 path는 RoboRev service, daemon, CLI, Gate 또는 process를 호출하지 않으며, `/api/repos`와 `/api/export/reviews` upstream request는 모두 0이다. unsafe export adapter와 production call path는 제거했다. `roborev export reviews` CLI는 `ensureDaemon()` side effect 때문에 계속 N/superseded다.

Reviews Export CTA는 disabled 상태와 “RoboRev v0.64.0에서는 안전한 저장소 단위 export를 지원하지 않음”이라는 localized explanation을 표시한다. browser download, prompt/diff/content export, polling/SSE export, daemon start/restart, operation manager/lease, CI metrics와 실제 RoboRev/daemon/LLM/external review 실행은 없다. Deterministic fake-daemon regression coverage는 identity collision race와 empty-identity name-fallback race를 각각 고정하고, 두 blocked path 모두 upstream inventory/export request, CLI/process와 browser download가 0임을 검증한다.

### transport

stable JSON CLI를 우선한다. v0.64.0의 `review` 명령에는 JSON launch receipt가 없으므로 새 review는 감지된 daemon endpoint의 public `/api/enqueue` 계약을 version capability로 캡슐화한다. Dashboard가 요청 시점에 Git으로 `HEAD`를 full SHA로 고정해 daemon에 전송하고, enqueue receipt와 동일한 fresh repository metadata를 browser에 반환하므로 실제 target이 audit 가능하다. UI는 실행되지 않는 CLI command preview를 만들지 않는다.

`/api/job/rerun`은 v0.64.0 upstream에서 기존 frozen target과 resolved agent/panel config를 복제한다. 이 기능은 `Rerun same target/config`로만 노출하고 새 HEAD review와 request type, endpoint 및 UI 위치를 공유하지 않는다. Dashboard의 generic frozen-rerun adapter와 UI는 `job_type=task` 또는 `git_ref=run`인 job을 거부하거나 숨기고 `phase=task-rerun-unsupported`를 반환한다. 따라서 Tasks execution-disabled policy를 우회하는 rerun은 없으며 Tasks 자체에는 rerun을 지원하지 않는다.

v0.64.0의 `repo list`에는 JSON이 없다. 초기 vertical slice는 Dashboard registry의 canonical Git repositories를 사용한다. human-readable `repo list` parsing은 core path에 넣지 않으며 향후 official JSON/API capability가 있을 때 추가한다.

v0.64.0에는 effective review panel을 열거하는 machine-readable CLI나 daemon API도 없다. Dashboard는 같은 버전의 upstream 계약에 맞춘 typed BurntSushi TOML decoder로 `ROBOREV_DATA_DIR/config.toml` 또는 `~/.roborev/config.toml`의 global `[review]`와 등록된 root의 `.roborev.toml`만 read-only로 읽는다. config entry는 플랫폼별 no-follow handle로 열고 handle의 regular-file metadata를 확인하며 1 MiB+1 byte까지만 읽어 oversized/special file을 fail closed한다. subagent/panel map은 global과 local의 합집합이며 같은 이름은 local entry 전체가 override한다. Browser에는 panel 이름, member 이름, synthesis/backup agent와 global/local origin만 보내며 instructions, model, provider, secret 및 나머지 config는 보내지 않는다. malformed 또는 구조적으로 resolve할 수 없는 config는 `none`으로 fallback하지 않고 Review HEAD를 막는다. Dashboard의 fallback은 registered root에 직접 존재하는 `.roborev.toml`까지만 지원하며, v0.64.0의 untracked main-checkout config를 linked worktree에 상속하는 특수 규칙은 구현하지 않는다. local config가 없는 경우에만 `.git` regular-file layout을 ambiguous로 분류하며, 이때 Git metadata가 실패하거나 누락되면 global named panel을 노출하지 않고 panel discovery/mutation을 fail closed한다. typed `git rev-parse --path-format=absolute --git-dir --git-common-dir` 결과가 다른 actual linked worktree만 ambiguous 상태에서 global named panel을 숨기고 명시적인 `Single agent · no panel`만 제공한다. submodule, separate-git-dir와 ordinary checkout은 metadata가 같아 global panel을 유지한다.

### process 실행

외부 process는 shell 없이 executable과 argument slice로 실행한다. stdout/stderr는 분리하고 각각 상한을 적용한다. request cancellation과 timeout을 전달하고 `WaitDelay`로 pipe 대기를 제한한다. Windows에서는 child를 kill-on-close Job Object에 넣어 timeout/cancellation 시 descendant까지 종료한다. daemon start만 background daemon 생존을 위해 이 tree ownership을 명시적으로 제외한다. audit metadata에는 executable basename, args, duration, exit code, truncation 여부만 기록하며 환경 변수 전체를 남기지 않는다. `Command.Stdin`/`StdinLimit`/`DefaultStdinLimit`은 사용처가 없어 의도적으로 제거되었다; 향후 bounded stdin이 필요한 프로토콜은 별도 검토된 typed 계약으로만 재도입한다.

### Live event relay

`roborev stream --repo <registered canonical path>`는 exact v0.64.0에서만 capability를 열며, stream 시작 전 CLI `Installation` version/capability와 daemon health의 typed `Version`이 모두 supported이고 서로 일치하며 daemon이 already-online/healthy인지 확인해야 한다. offline daemon을 자동 시작하지 않으며 unsupported/failed stream은 기존 API와 polling을 방해하지 않는다. typed argv와 immutable binary snapshot을 사용하고 shell, stdin, generic command endpoint는 없다.

Backend는 repository identity별 RoboRev source 하나와 `0..N` browser subscribers를 소유한다. JSONL stdout은 bounded line reader(1 MiB), stderr는 bounded sink(64 KiB)로 처리하고 malformed/unknown/oversized line, process exit, cancellation과 shutdown을 안전하게 처리한다. recognized `job.enqueued`, `review.started`, `review.completed`, `review.failed`, `review.canceled`, `review.remapped`만 sequence를 증가시키며 raw payload를 버리고 `jobs-changed` 하나의 invalidation signal로 축약한다. subscriber channel은 한 칸이며 burst를 nonblocking coalesce하고 source 재시작은 subscriber가 남아 있고 daemon gate가 다시 healthy할 때만 bounded backoff로 시도한다. 마지막 subscriber 뒤에는 짧은 idle grace를 두되 reconnect가 source를 중복 생성하지 않게 하며, `Server.BeginShutdown`이 HTTP shutdown 전에 source와 child를 취소한다.

`GET /api/events?repositoryIdentity=<opaque>`는 source startup side effect를 가지므로 browser request의 same-origin을 fail-closed하게 증명한 뒤에만 query/registry/subscribe를 수행하는 SSE다. explicit `Origin`은 정확히 하나의 fully formed origin이어야 하며 request의 scheme+host와 exact match해야 한다. `Origin`이 없을 때는 native same-origin EventSource 계약인 `Sec-Fetch-Site: same-origin`, `Sec-Fetch-Mode: cors`, `Sec-Fetch-Dest: empty`가 각각 정확히 한 번씩 있어야 허용한다. foreign, `null`, malformed, blank, duplicate Origin과 누락·중복·다른 Fetch Metadata는 403이며, SSE에는 CSRF token을 요구하지 않는다. mutation은 non-browser/local client 호환성을 위해 기존 absent-Origin 허용과 CSRF semantics를 유지한다. query shape도 strict하게 검사하고 응답에는 `{repositoryIdentity,sequence,kind}`만 보낸다. prompt, diff, log, agent output, credential 가능 필드와 raw stderr/error는 브라우저로 전달하지 않는다. stream은 **lossy refresh/invalidation hint**이며 상태를 직접 표현하지 않는다. frontend는 `jobs-changed`를 받으면 burst를 짧게 coalesce/debounce하고 existing `/api/reviews` **authoritative API = actual state**를 다시 읽는다. repository epoch가 다른 event/late response는 무시하고 EventSource reconnect를 유지한다. 기존 4초 review polling은 제거하지 않으며 **4초 polling = fallback/safety net**이다.

Manager는 single identity ownership/state machine으로 identity별 source 하나, shared startup result, subscriber cancellation, idle-generation cleanup과 bounded restart를 관리한다. `Subscribe`는 opaque identity만 받고 initial start와 모든 restart 직전에 registry authorizer로 identity를 fresh resolve하므로 stale/fallback path를 재사용하지 않으며, 마지막 subscriber가 사라지거나 Dashboard shutdown이 시작되면 source context와 child를 정리한다.

### repository registry

server가 canonical absolute path만 등록한다. 등록 시 `.git`을 확인하고 `git -C <path> rev-parse --show-toplevel` 결과가 같은 root인지 검증한다. canonical path identity는 Windows에서 case-insensitive, case-sensitive platform에서 exact spelling으로 중앙화한다. 등록된 path의 fresh inspection 결과와 startup 시 persisted path를 다시 load한 결과도 expected identity와 일치하는지 검증해 junction/symlink retarget으로 다른 Git root가 authorization되거나 Review target이 되는 것을 거부한다. Browser에는 backend가 생성한 opaque repository identity를 correlation key로 제공하며, mutation authorization에는 계속 canonical path만 사용한다. path를 받는 mutation과 일반 global job/panel read는 daemon metadata lookup으로 owning repository를 확인하되, lazy Prompt/Log는 v0.64.0의 queued/running prompt 보존 semantics 때문에 아래 전용 prefix-only ownership proof를 사용한다. recent repository, last selected repository와 platform-aware identity별 마지막 panel preference만 `os.UserConfigDir()/roborev-dashboard/config.json`에 저장하며 credential은 저장하지 않는다. Add/Select/panel preference는 prospective state 저장이 성공한 뒤에만 in-memory 상태를 갱신한다. 저장된 panel은 authorization이 아니며 current effective config에서 다시 발견될 때만 사용한다.

### HTTP 보안

기본 bind는 `127.0.0.1`이다. mutation request는 exact Host, allowed Origin과 per-process CSRF token을 검증한다. request body에 repository path가 있더라도 registry에서 다시 resolve한다. generic command API는 없다.

### 데이터와 UI 상태

review 목록은 v0.64.0의 `/api/jobs?repo=...&omit_prompt=true`를 사용하며, 각 요청 완료 4초 후 다음 요청을 예약해 겹치는 poll을 만들지 않는다. polling이 가능한 selected repository는 첫 current-generation 목록 요청이 성공 또는 실패로 settle되기 전까지 empty state와 Review HEAD를 gate한다. repository 전환과 unmount는 generation을 무효화해 이전 응답과 오류가 새 상태를 덮거나 새 repository의 initial gate를 해제하지 못하게 한다. background refresh 오류는 반복 toast가 아니라 deduplicated inline 상태로 표시한다. 목록 polling은 known heavy fields를 adapter에서 제거하며 Panel Refine은 별도 `/api/job/output` status-prefix 계약을 사용해 active prompt/lines를 수신하지 않는다. `list --json`은 full prompt와 diff를 포함하므로 주기 경로에서 사용하지 않는다. detail, prompt와 log는 별도 endpoint에서 사용자가 tab을 선택할 때만 읽는다. panel synthesis를 actionable parent로 우선 표시하고 member metadata는 같은 `panel_run_uuid`의 v0.64.0 full-run `/api/jobs?panel_run=...&limit=0&omit_prompt=true` 결과에서 synthesis 1개와 member rows를 함께 받아 lazy-load/polling한다. `GET /api/panels/{run}/members`는 opaque `repositoryIdentity`와 synthesis `parentJobId`를 필수로 받아 response 자체의 정확히 하나인 synthesis row를 parent로 bind하고 parent ID, repository, run, panel, `panel_role=synthesis`와 `job_type=synthesis` 및 모든 row의 positive unique ID를 fail closed하게 검증한다. 별도 parent `JobMetadata` lookup은 반복 poll 경로에서 사용하지 않는다. member tree는 upstream status, verdict, member name, agent, model과 duration을 그대로 표시하고 metadata만으로 terminal/total 진행률을 계산한다. member 원문은 사용자가 선택한 job 하나에만 panel-scoped `GET /api/panels/{run}/members/{memberId}`를 사용한다. backend가 같은 parent/run/repository의 실제 member임을 다시 확인한 뒤 typed `show --job <id> --json`을 호출하고 Show 자체의 `job_id`, nested job ID, repository, run과 role도 검증한다. synthesis가 재가공한 내용이나 Dashboard 번역 결과로 대체하지 않는다. 선택 전 member output을 선조회하지 않고, parent/member list/member detail/prompt·log loading을 분리하며 repository/panel/member scope token과 generation으로 새 scope의 첫 skeleton, 동일 scope background refresh, 늦은 detail 응답의 stale 반영을 구분한다. terminal reconciliation이 initial detail 요청을 supersede하면 current generation이 success/final failure 뒤 `detailLoading` 종료를 소유하고 stale finally는 state를 변경하지 않는다. terminal log refresh의 실패는 generation-aware lazy error와 retry UI로 표시한다. cancel/rerun/close 같은 panel action과 전체 verdict는 계속 synthesis parent 기준이다. mutation 성공 후 목록을 RoboRev source of truth에서 다시 fetch한다. 목록 window 밖 selected job의 authoritative refresh는 `GET /api/reviews/{id}?repositoryIdentity=<opaque>`를 사용하며 backend가 identity를 등록 경로로 resolve한 뒤 `JobMetadata`의 canonical repository를 `gitx.SameRepositoryPath`로 확인하고 일치할 때만 Show를 실행한다. frontend는 path equality를 보안 경계로 재구현하지 않으며, mutation 전후 bootstrap도 captured repository identity와 현재 identity가 계속 일치할 때만 적용해 A→B late response를 버리고 A→B→A current target은 허용한다. Live event relay는 이 목록을 직접 수정하지 않고 **lossy refresh/invalidation hint**만 제공하며 `/api/reviews` **authoritative API = actual state**, **4초 polling = fallback/safety net** 관계를 유지한다. 이벤트 burst는 frontend에서 coalescing/debounce하고 repository switch 뒤 stale event와 late response를 거부하며, SSE unavailable/reconnect 중에도 polling을 계속한다.

repository 전환 시 panel catalog도 별도 current-generation request로 읽는다. valid saved preference가 있으면 복원하고, named panel이 하나면 자동 선택하며, 여러 개면 사용자 선택 전까지 Review HEAD를 막고, named panel이 없을 때만 reserved `none`을 자동 선택한다. 사용자가 선택하거나 Review HEAD를 누를 때 backend는 fresh repository identity와 current TOML을 다시 resolve해 exact panel 또는 built-in `none`만 daemon JSON enqueue에 전달한다.

### 화면과 작업 진입점

Sidebar의 `Fix & Refine`는 더 이상 placeholder가 아니다. 기존 Panel Refine 화면은 이 화면의 full workflow surface로 이동하고, General Fix의 terminal F single review와 panel synthesis parent도 같은 화면에서 선택한다. `Reviews`는 review 목록과 상세를 계속 소유하되 Panel Refine의 전체 조작 화면을 중복 렌더링하지 않는다. active 또는 `needs_attention`인 Panel Refine이 있으면 `Reviews`에는 compact summary만 표시하고, 사용자가 `Fix & Refine`로 이동해 해당 operation을 재개한다. Summary의 링크와 operation의 repository identity/generation은 현재 선택 repository와 일치할 때만 동작한다. `Review HEAD`와 `Rerun same target/config`는 계속 별개의 primary/advanced action이며 General Fix 진입점으로 재사용하지 않는다.

### Frontend localization

`web/src/i18n.tsx`는 English source catalog와 exact-key Korean catalog, `Locale = 'ko' | 'en'`, `roborev-dashboard-language` storage key, guarded storage access와 browser fallback을 한 곳에서 소유한다. `I18nProvider`의 `t`/`format` callback은 locale 전환에도 stable identity를 유지하고 `<html lang>`만 presentation 상태로 갱신한다. App은 stable navigation/repository/panel/review IDs와 번역된 표시 label을 분리하며 locale 변경을 fetch/effect dependency나 React key/remount 조건으로 사용하지 않는다.

Language selector는 sidebar footer와 overlay가 가리는 다섯 개의 confirmation surface(install, daemon, agent check, Fix Prompt, Panel Refine) 헤더에 배치한다. 전환은 현재 repo, panel, detail/tab, modal, setup/progress/refine/agent/runtime/form/search/comment 상태를 유지하고 새 network request나 mutation을 만들지 않는다. Dashboard가 만든 chrome/empty/loading/error/action 문구만 번역하며 RoboRev, Git/SHA/API/CLI/CSRF/URL/JSON, paths, versions, names, branches, IDs, executable argv와 backend/RoboRev raw error는 source of truth로서 보존한다. English fallback은 누락 key를 안전하게 표시하고 typed catalog가 build 단계에서 key drift를 검출한다.

`GET /api/reviews/{id}/fix-prompt`는 job ownership과 current registered repository를 확인하고 `show --job --json`을 lazy-load한 뒤 요청한 single review, panel synthesis 또는 individual panel member의 top-level finding output과 최소 metadata만 typed decode한다. terminal F 결과에 한해 deterministic Korean template를 생성하며 LLM, `roborev fix`, mutation, close 또는 rerun을 실행하지 않는다. prompt, diff, log, comments, 다른 member의 aggregate와 config는 포함하지 않고 finding은 변형하지 않는다. target과 current HEAD가 다르면 stale warning을 넣으며 input/output 크기는 bounded하고 초과 시 truncate하지 않고 거부한다.

Dashboard의 `/api/runtime`은 repository inspection이나 review listing 없이 TTL 30초의 version detection과 v0.64.0의 작은 `/api/health`만 수행하며 UI가 10초마다 호출한다. 실제 `status --json`은 최근 job의 full prompt까지 포함할 수 있어 주기적 polling transport로 사용하지 않는다. panel member도 목록에 합치지 않고 panel tab을 열 때 `/api/jobs?panel_run=...&limit=0&omit_prompt=true`의 v0.64.0 full-run 응답(멤버 + 정확히 하나의 synthesis)을 받아 검증한다. backend member list/detail은 요청의 opaque repository identity를 registry에서 resolve하고 `gitx.SameRepositoryPath`로 권한 경계를 재검증한다. member list는 매 poll에 PanelMembers 1회만 호출하며 parent JobMetadata를 호출하지 않는다. nonterminal member가 있는 동안 4초마다 갱신하고, `limit=0`은 unlimited로 문서화되어 있다.

### Panel Refine

Panel Refine은 React effect가 아니라 Dashboard backend process가 소유하는 typed state machine이다. API는 `POST /api/panel-refines`, `GET /api/panel-refines`, `GET /api/panel-refines/{id}`, `POST /api/panel-refines/{id}/cancel`로 구성되며, Browser는 시작·상태 조회·취소만 요청한다. browser reload나 tab close는 active run을 중단하지 않는다. 이 checkpoint의 run은 process-scoped이므로 Dashboard process가 종료되면 active run context와 child process가 취소되고, 재시작 뒤 자동 resume하지 않는다. active run은 `reviewing`, `evaluating`, `fixing`, `final_reviewing`, `passed`, `needs_attention`, `failed`, `cancelled` 같은 명시적 phase와 iteration/fix/review receipt를 보존한다.

시작 시 registered repository의 canonical identity를 fresh inspection으로 재검증하고, clean working tree·branch·HEAD를 확보한다. iteration panel과 선택한 optional final panel은 현재 Panel Resolver에서 다시 resolve하며, fix agent는 typed allowlist로 제한한다. 기본 max fix attempts는 3이고 허용 범위는 1~10이다. 같은 repository identity에는 process-scoped lock을 두어 동시에 두 Panel Refine을 시작하지 않으며, active run 동안 해당 repository의 `Review HEAD`, `Rerun same target/config`, 다른 Panel Refine start도 backend에서 거부한다. read-only 조회는 계속 허용한다.

각 iteration은 fresh `Inspect` 결과의 full SHA와 branch를 사용해 새 panel review를 enqueue한다. 기존 frozen target을 재실행하는 Rerun은 사용하지 않는다. enqueue receipt에는 synthesis job ID, panel run UUID, repository path, full `git_ref`, branch, panel, synthesis role과 panel job type이 모두 있어야 하며 요청한 identity와 일치하지 않으면 중단한다. v0.64.0 Panel Refine status는 `/api/job/output?job_id=...`의 ordered `job_id,status,lines,has_more` 응답에서 8 KiB 이하 prefix만 읽고 `lines` 값 직전에 response를 닫는다. `Content-Type`, HTTP status, key order, job ID와 malformed prefix를 검증하며 v0.64.x 밖의 capability와 4xx contract 오류는 fail closed한다. `queued`/`running` 중에는 metadata를 요청하지 않고, 첫 `done`에서만 `omit_prompt=true` terminal metadata를 최대 256 KiB로 bounded fetch해 receipt의 repository/ref/branch/panel/run UUID/role/type, skipped, status와 P/F verdict를 모두 재검증한다. transport/5xx 오류만 제한된 backoff retry하며 unknown/canceled/failed/skipped/malformed/identity mismatch는 PASS로 취급하지 않고 `failed` 또는 `needs_attention`으로 중단한다. iteration panel이 PASS하고 final panel이 명시되면 final panel도 같은 HEAD에서 별도로 검증한다. 두 panel이 같으면 중복 review를 하지 않는다. final panel의 F도 같은 fix budget을 사용하며, fix 뒤에는 항상 iteration panel부터 새 HEAD를 검증한다.

이번 checkpoint에서는 Codex만 허용하는 fix adapter가 v0.64.0의 확인된 typed command인 `roborev fix --agent codex --quiet <synthesis-id>`를 configured executable과 argument array로 실행한다. synthesis/parent job ID만 전달하고 finding text, prompt, diff 또는 arbitrary executable을 argv에 넣지 않는다. fix 성공 뒤에도 fresh inspection으로 repository identity와 branch가 동일하고 working tree가 clean하며 HEAD가 실제로 전진했는지 확인한다. HEAD 불변, dirty tree, branch 변경, identity drift, authorization 상실 또는 fix/review 오류는 자동으로 다음 iteration으로 넘기지 않고 `needs_attention`/`failed`로 중단한다.

process-scoped manager(refine, fixoperation, setup, runtimecontrol)의 Start acceptance와 Shutdown은 같은 manager mutex 아래에서 선형화된다. `closing` 플래그가 등록(`wg.Add` equivalent)과 함께 원자적으로 검사되므로, validate/preflight 중인 Start가 shutdown 시작 뒤에 추적되지 않은 채 등록되어 Shutdown 반환 후 work를 남기는 race는 구조적으로 존재하지 않는다. Shutdown은 새 acceptance를 닫은 뒤 active cancel과 wait를 수행한다.

Review 완료 직후의 재검증과 repository identity lock은 사용자가 외부에서 commit, edit, checkout 또는 path retarget을 한 stale finding의 자동 적용을 막는다. 각 enqueue, polling, fix에는 짧은 bounded timeout을 두며 전체 run에도 명시적인 safety ceiling을 둔다. 취소 중 review는 RoboRev cancel을 best-effort로 호출하고, 취소 중 fix는 context cancellation으로 child process를 중단한다. 취소 후 fresh inspection 결과는 `cancelState`의 availability, HEAD, branch, dirty 및 inspection error로 run에 기록하며 clean을 추측하지 않는다.

v0.64.0의 `fix`는 fix agent가 새 commit을 만든 뒤 panel 없는 default review를 자동 enqueue할 수 있다. Dashboard는 선택한 panel의 새 HEAD review를 별도로 enqueue하므로, 이 upstream 동작으로 unrelated extra review가 생길 수 있다. Dashboard는 응답이나 이름만으로 이를 추측해 억제하지 않으며, 해당 중복 제거는 upstream capability가 제공될 때 별도 version-gated 계약으로 다룬다.

### General Fix

General Fix는 Panel Refine의 반복 workflow와 별개인 명시적 단일 fix operation이다. Dashboard가 지원하는 exact RoboRev v0.64.0의 upstream contract는 positive decimal job ID를 positional target으로 받는 `fix --agent codex --quiet <job-id>`다. v0.64.0의 `fix`는 현재 checkout에서 agent를 실행하며 시작 시 dirty tree나 review target의 stale HEAD를 차단하지 않는다. stdout/stderr는 machine-readable 결과 계약이 아니고, exit 0도 no-change 또는 dirty worktree인 채 job이 닫힌 경우를 배제하지 않는다. commit이 생성되면 RoboRev가 panel 없는 default review enqueue를 시도할 수 있으므로 Dashboard는 그 부수 job을 성공 근거로 추측하거나 억제하지 않는다. 이 동작은 [v0.64.0 fix source](https://github.com/kenn-io/roborev/blob/v0.64.0/cmd/roborev/fix.go)와 [assisted-refactoring guide](https://github.com/kenn-io/roborev/blob/v0.64.0/docs/guides/assisted-refactoring.md)를 기준으로 version-gated 한다.

Dashboard는 upstream의 느슨한 실행 전제를 안전 경계로 보강한다. 요청은 선택된 registered repository의 opaque `repositoryIdentity`와 positive `targetJobId`만 받으며, backend가 fresh registry/ownership lookup과 job metadata를 다시 확인한다. 대상은 명시적으로 `status=done`, `verdict=F`, `closed=false`, `skipped=false`인 terminal review여야 하며 single review 또는 panel synthesis parent만 허용한다. panel member ID, synthesis가 아닌 다른 panel row, PASS/running/canceled/closed job은 General Fix 대상이 아니다. 시작 시 current branch와 target job의 full `git_ref`/HEAD가 같고 working tree가 clean이어야 한다. stale, dirty, branch/identity drift는 자동 보정하지 않고 conflict로 거부한다.

Preview/prepare 단계는 backend가 fresh authorization으로 만든 opaque preview token과 exact executable/argument array를 반환한다. Browser는 executable, job ID 이외의 argv, finding text, prompt, diff 또는 arbitrary command를 제출하지 않으며, preview에 표시된 command가 confirmation 대상이다. 확인 POST는 token을 재사용하더라도 repository, target, branch, HEAD, clean state와 authorization을 다시 검사하고 같은 typed command builder로 argv를 다시 생성한다. Browser request의 lifetime과 분리된 process-scoped manager가 operation을 `running`, `succeeded`, `failed`, `cancelled` 같은 명시 상태로 소유한다. API는 `GET /api/fixes/preview`, `POST /api/fixes`(확인된 실행), `GET /api/fixes`, `GET /api/fixes/{id}`, `POST /api/fixes/{id}/cancel`을 제공하며, cancel과 Dashboard shutdown은 context와 child process를 정리한다. browser disconnect나 reload는 실행을 암묵적으로 취소하지 않고, process restart 뒤 active operation을 resume하지 않는다.

General Fix는 shared global operation gate와 repository-scoped lease를 사용한다. global gate는 Setup/runtime control/Panel Refine/Review·Rerun을 포함한 다른 mutation과 active Fix를 상호 배제하고, repository lease는 Panel Refine 및 Review/Rerun과 같은 repository의 worktree 경쟁을 fail-fast conflict으로 거부한다. read-only 조회는 허용한다. process runner는 shell 없이 validated executable과 argument slice를 사용하며 stdout/stderr와 오류는 bounded status/error summary만 보존한다. 실행 완료 후 backend는 fresh Git inspection으로 같은 registered identity와 branch, HEAD advancement, clean tree를 모두 확인한다. exit 0이더라도 commit/HEAD가 전진하지 않았거나 dirty, branch 변경, identity drift, process/cancel/timeout 오류가 있으면 성공으로 표시하지 않고 `failed` 또는 `cancelled`로 남긴다. 성공·실패·취소 뒤에는 UI 추측 상태를 갱신하지 않고 Reviews와 Fix & Refine의 authoritative API를 다시 조회한다.

### Tasks

Tasks는 **history-only** 화면이다. v0.64 Custom Task 실행은 fail-closed로 비활성화되어 있다. 이유는 다음과 같다.

- RoboRev `run`의 job-level 기본은 non-agentic이지만, upstream Codex agent는 `agenticMode := a.Agentic || AllowUnsafeAgents()`로 daemon effective global config를 함께 본다. `allow_unsafe_agents=true` 또는 `disable_codex_sandbox=true`인 daemon은 job-level `Agentic:false` 뒤에서도 더 위험한 mode로 task를 실행할 수 있다.
- daemon이 실제로 사용하는 config identity와 effective safety state를 증명하는 machine-readable contract가 v0.64에는 없다. `/api/health`, `/api/status`, OpenAPI 어디에도 config path/identity나 effective `allow_unsafe_agents`/`disable_codex_sandbox` 값이 노출되지 않으며, `roborev status --json`도 version/queue metadata만 제공한다.
- Dashboard process가 읽는 global config file은 각 process 자신의 environment(`ROBOREV_DATA_DIR` 포함)에 의존하므로, 그것을 daemon의 effective state로 가정하는 것은 추측이다. read-only safety authorization은 추측해서는 안 된다.

따라서 Dashboard에는 `run` enqueue command builder, receipt parser, task preflight/safety adapter, preview token, task manager와 task execution lease가 존재하지 않는다. `POST /api/tasks/preview`와 mutation authorization(same-origin/CSRF) 뒤의 `POST /api/tasks`는 service/registry/process를 호출하지 않고 `501 phase=task-execution-disabled` tombstone을 반환한다. Frontend composer는 inspection-only(disabled textarea)이며 실행 CTA가 없고 `/api/tasks*`를 호출하지 않는다. UI와 backend 양쪽 모두에서 production reachable한 custom task enqueue 경로는 0이다. Analyze가 upstream 자체가 `Agentic:true`라서 막힌 것과 달리 Tasks는 "effective safety를 증명 불가"라서 막혀 있으므로, 두 disable 사례를 하나의 generic unsafe-agent manager로 합치지 않는다.

기존 기능은 유지된다. Task history는 `/api/reviews`의 `job_type=task` + `git_ref=run` rows와 SSE `jobs-changed` + 4초 polling fallback으로 조회하고, 결과는 기존 ReviewDetail lazy detail path로 연다. Generic frozen rerun은 `job_type=task` 또는 `git_ref=run`을 거부·숨기고 `phase=task-rerun-unsupported`를 반환한다. 이 차단이 없으면 generic rerun이 execution-disabled policy를 우회하는 통로가 되므로 execution disable 이후에도 유지한다. 향후 재검토 조건은 upstream이 daemon effective safety attestation을 공식 machine-readable 계약으로 제공하고 capability로 확인될 때뿐이다.

### Analyze

Analyze는 exact v0.64.0 `analyzeIntrospection=true` capability로만 열리는 introspection-only catalog/prompt 경로다. execution capability는 노출하지 않는다. type discovery는 bounded human-readable `roborev analyze --list`를 strict typed parser로 읽고, `Available analysis types:` header, safe-slug 이름, nonempty description, 중복 금지와 reasonable count/output bound를 검증한다. prompt는 사용자가 선택한 type에 대해 lazy하게 `roborev analyze <type> --show-prompt`를 호출한다. RoboRev가 반환한 type name, description과 prompt template은 source of truth이며 Dashboard는 locale에 따라 번역하거나 재작성하지 않는다.

backend가 사용하는 introspection exact argv는 다음 두 가지다.

```text
list:       roborev analyze --list
prompt:     roborev analyze <type> --show-prompt
```

v0.64 Analyze enqueue는 upstream의 verified contract상 `Agentic: true`이며 worker도 `WithAgentic(true)`로 구성된다. Edit/Write/Bash 권한을 포함한 agentic 작업은 Dashboard가 임의로 실행하면 안 되므로, Dashboard에는 enqueue command builder, receipt DTO/parser, execution capability 또는 실행 service method가 없다. 따라서 `GET /api/analyses/preview`와 CSRF/Origin 보호 뒤의 `POST /api/analyses`는 모두 process/service를 호출하지 않고 `501 phase=analysis-execution-disabled` tombstone을 반환한다. JSON execution coverage는 P/disabled다. 향후 upstream이 agentic 안전 정책, 명시적 preview/confirmation 계약과 non-agentic 또는 별도 승인 transport를 제공하고 capability로 확인될 때만 재검토한다.

Analyze manager는 operation history, preview token, confirmation, registry lease, execution gate 또는 별도 job lifecycle을 저장하지 않는 stateless catalog/prompt adapter다. GET types/prompt와 SSE는 strict browser read authorization 뒤에만 service/stream을 호출한다. explicit Origin은 정확히 하나의 same scheme+host이거나, Origin이 없을 때 `Sec-Fetch-Site: same-origin`, `Sec-Fetch-Mode: cors`, `Sec-Fetch-Dest: empty`가 각각 정확히 하나여야 한다. foreign/null/blank/malformed/duplicate Origin과 missing/duplicate/wrong metadata는 query, registry, service 전에 403이다.

health adapter는 다른 runtime/stream 계약과 동일하게 bounded body, `DisallowUnknownFields`, exactly one JSON value, `healthy`와 version 검증을 유지한다. `$schema`는 missing 또는 임의 JSON string이면 허용하고, present null/non-string은 거부한다. 실제 Analyze enqueue, daemon mutation 또는 LLM smoke는 자동 검증에서 실행하지 않는다.

### Configuration

Configuration은 exact v0.64.0의 `configIntrospection`/`configMutation` capability로만 열리는 bounded config surface다. `config list/get/set`은 filesystem/CLI operation이므로 조회에 daemon online을 요구하지 않고 Dashboard가 조회를 위해 daemon을 시작하지도 않는다.

backend exact argv는 세 가지다.

```text
list: roborev config list --show-origin
get:  roborev config get <key> --global|--local   (allowlisted post-write verification만)
set:  roborev config set <key> <value> --global|--local
```

`config list --show-origin`은 사람용 tabwriter text이므로 fail-closed parser로 읽는다. row는 `<origin><key><value>` 순서며 origin은 global/local/default allowlist, key는 safe charset, 첫 두 column을 분리한 나머지 전체를 value로 보존해 공백 포함 값을 잃지 않는다. unknown origin, duplicate key, malformed row, control character(NUL/DEL/C0), line/row count bound, total output bound(256 KiB) 위반은 전부 reject한다. sensitive 값은 upstream이 이미 mask한 텍스트 그대로 표시하며 Dashboard는 raw secret을 재조회하거나 unmask하는 endpoint를 제공하지 않는다.

수정 가능한 설정은 backend가 소유하는 typed allowlist(`internal/configuration`)뿐이다: `max_workers`(global only, 1..32), `review_context_count`(0..20), `auto_close_passing_reviews`, `review_reasoning`, `refine_reasoning`(enum), `review_min_severity`, `fix_min_severity`, `refine_min_severity`(빈 값=filtering disabled 포함 enum). integer bound는 upstream generic parser와 별개인 Dashboard safety policy다. `allow_unsafe_agents`, `disable_codex_sandbox`, `server_addr`, `*_cmd` override, credential, panel/subagent/hook/ACP 등은 v1 mutation surface에서 영구 제외며 browser는 key/type/scope/validation을 결정하지 못하고 POST의 arbitrary key는 backend가 거부한다.

flow는 preview → explicit confirmation → set이다. `POST /api/configuration/preview`(same-origin+CSRF)는 fresh repository identity resolve/canonical inspection/local dirty 검사/exact v0.64 binding 후 typed request(integer/boolean/enum JSON)를 canonical CLI string으로 변환하고, current effective row와 snapshot digest(SHA-256 of parsed rows)를 계산해 single-use random token에 bind한다(browser에는 opaque token만 전달). response는 exact executable+argv preview와 warning codes(local: `.roborev.toml` 수정/tracked 시 dirty/TOML normalize, global: normalize)를 담는다.

`POST /api/configuration/set`은 exclusive operation gate(AcquireFix)를 먼저 획득한 뒤 token을 소비(single-use, TTL)하고, local scope면 repository lease를 잡는다. local lease가 busy이면 token을 restore해 동일한 유효 token으로 재시도할 수 있으며, 만료 token은 restore하지 않는다. 그 뒤 identity/path/head/branch/dirty/binary generation/snapshot digest를 모두 fresh 재검증한다. 하나라도 다르면 stale로 reject하고 RoboRev를 실행하지 않는다. `config set` 성공만으로 끝내지 않고 scoped `config get <key>` readback이 요청 canonical value와 일치하는지 확인한 뒤 merged `config list`를 fresh 실행해 응답에 담는다. post-start failure(timeout/nonzero/readback 불일치/list 실패)는 "변경되지 않았다"고 단정하지 않고 `status=unverified` 결과로 보고하며 자동 rollback하지 않는다. local 변경 성공 후 fresh inspection으로 dirty 상태를 UI에 안내하고 commit/revert는 사용자 몫이다.

GET `/api/configuration`과 preview/set authorization은 Analyze/SSE와 동일한 strict browser read / same-origin+CSRF 정책을 공유하며 authorization 실패 시 process를 시작하기 전에 거부한다. snapshot handler도 service 구현에 의존하지 않고 exact v0.64 introspection capability를 직접 확인한 뒤에만 `ConfigList`를 호출한다. frontend는 snapshot과 preview에 별도 generation/ownership을 두어 repo switch, capability disable, draft value/scope 변경, Cancel과 unmount에서 pending/open preview를 무효화하고 stale `finally`가 새 preparing state를 지우지 못하게 한다. confirm double click은 정확히 한 POST가 되게 보장하며 locale 전환은 config GET/preview/set을 재실행하지 않는다.

### Stats & Insights

Stats v1은 현재 선택된 registered repository 하나의 read-only aggregate workspace다. exact v0.64.0의 `summaryStats`/`costStats` capability와 already-online healthy daemon이 모두 확인될 때만 동작하며 Dashboard가 daemon을 자동 시작하거나 재시도 polling을 만들지 않는다. Browser는 opaque `repositoryIdentity`, allowlisted window(`24h`, `7d`, `30d`, `90d`), semantic branch scope(`all`, `current`)만 전송한다. raw path, branch name, arbitrary since expression과 all-repositories aggregate는 지원하지 않는다.

backend는 strict browser read authorization을 query/registry/process보다 먼저 적용한다. `all`과 `current` scope 모두 fresh repository inspection으로 등록된 identity가 여전히 같은 canonical root를 가리키는지 다시 검증하고, `current`는 여기서 authoritative branch도 얻는다. canonical root drift와 explicit detached-HEAD state, empty/`HEAD` current branch는 fail closed한다. Literal branch name `detached`는 attached branch로 허용한다. exact typed argv는 다음과 같으며 shell을 사용하지 않는다.

```text
summary all:     roborev summary --repo <canonical-root> --since <window> --json
summary current: roborev summary --repo <canonical-root> --branch <fresh-branch> --since <window> --json
cost all:        roborev cost --repo <canonical-root> --json
cost current:    roborev cost --repo <canonical-root> --branch <fresh-branch> --json
```

`GET /api/stats/summary`와 `GET /api/stats/cost`는 독립 endpoint와 failure state를 갖는다. 실행 전 CLI/daemon version이 exact v0.64.0으로 일치하는지 확인하며 unsupported/offline이면 Stats subprocess를 시작하지 않는다. daemon health는 하나의 strict bounded parser를 공유하되 browser-hidden typed probe state(Online/Offline/Invalid/Unknown), semantic condition(Healthy/Unhealthy/Unknown)과 daemon version을 분리한다. top-level JSON object와 required non-null boolean `healthy`만 허용하며 concrete connection-loss errno만 offline/503으로 분류한다. reachable HTTP·JSON·schema·size contract 오류와 그 밖의 non-offline transport 오류는 invalid/502로 fail closed하고 사람이 읽는 `Installation.Error` 문자열은 분기 근거로 사용하지 않는다. 전역 `Installation.Status.running`은 valid health endpoint의 reachability를 뜻하므로 `healthy:false`여도 true를 유지한다. Stats HTTP precheck는 typed probe, condition과 exact supported CLI/daemon version pair만 사용해 unhealthy/offline/version incompatibility를 503, invalid/unknown을 502로 거부하고 browser용 Status JSON을 재해석하지 않는다. adapter는 subprocess 직전에 fresh health/version preflight를 다시 수행해 snapshot 이후의 상태 변화도 fail closed한다. process는 context cancellation, timeout, 분리된 bounded stdout/stderr를 사용한다. Summary parser는 256 KiB, Cost parser는 64 KiB 한도에서 UTF-8, exactly one JSON value, recursive duplicate key, unknown field(known optional bounded string `$schema`만 허용), required object, 배열·문자열·map bound, JS-safe nonnegative count, finite rate/duration/cost와 count-derived rate를 포함한 upstream semantic invariant를 fail-closed하게 검증한다. 실제 v0.64 zero-data의 `agents:null`과 `job_types:null`은 stable empty arrays로 정규화한다.

Summary의 embedded `cost`는 선택한 window의 approximate cost이고 standalone Cost는 같은 repository/branch scope의 all-time approximate cost다. 둘을 비교하거나 합치지 않는다. UI는 항상 reported jobs의 lower bound와 `jobs_with_cost / jobs_total` coverage를 함께 표시한다. `jobs_total == 0`만 empty이고, eligible/reported job이 있으면서 `total_usd == 0`인 free aggregate는 데이터가 있는 `$0`로 표시한다. provider invoice 또는 실제 청구액이라고 표현하지 않는다.

Frontend Stats workspace는 Summary와 Cost 각각의 AbortController, generation과 captured scope를 소유한다. 페이지 진입, scope 변경, explicit Retry/Refresh에서만 조회하고 review 4초 polling/SSE에는 연결하지 않는다. foreground suspension 중에는 새 Stats read를 시작하지 않고 진입 시 in-flight read를 abort·무효화하며 loading state를 정리한다. render에서 즉시 갱신되는 suspension ref를 success/error completion handler도 확인하므로 render와 passive abort effect 사이의 완료 결과도 적용되지 않는다. suspension 해제 자체는 fetch trigger가 아니므로 기존 snapshot을 유지하고 사용자의 다음 scope 변경, Retry 또는 Refresh를 기다린다. window 변경은 Summary만, branch 변경과 Refresh는 두 endpoint를 독립 갱신한다. late window/branch/repository 응답은 폐기하며 locale 전환은 subprocess를 유발하지 않는다. Overview, Timing, Agents, Job types, Failure categories와 Window/All-time Cost를 cards/tables로 표시하고 새 chart dependency는 추가하지 않는다. `GuidelineInsights`는 이 lifecycle과 분리된 현재 실행 전용 preview/confirm/status/result 컴포넌트이며 Summary/Cost fetch를 소유하거나 트리거하지 않는다.

### Repository inventory

Repositories v2는 Dashboard Registry와 별개인 read-only RoboRev tracked-repository inventory다. exact v0.64.0의 typed daemon endpoint `GET /api/repos`를 query와 request body 없이 호출하며, 사람용 `roborev repo list` 출력, `repo show`, RoboRev storage DB와 SQLite에는 접근하지 않는다. 기능은 additive `repositoryInventory` capability와 optional `roborev.RepositoryInventoryService`에만 놓고 base review `Service`를 확장하지 않는다. 호출 전에는 기존 typed Installation 계약으로 installed/exact capability, daemon online+healthy, exact CLI/daemon version pair를 fresh 확인하며 inventory 조회를 위해 daemon을 시작하지 않는다.

Daemon response는 1 MiB 한도의 별도 strict parser가 UTF-8, exactly one top-level object, required non-null `repos`/`total_count`, row의 required `name`/nonempty `root_path`/`count`, optional string `identity`, unknown field 거부, nonnegative JS-safe integer와 `total_count == sum(count)`를 검증한다. empty inventory는 유효하고 upstream order와 path spelling을 보존한다. `count`는 `review_jobs` row 수이므로 Browser/UI에서는 항상 Jobs로 표현한다. Upstream `identity`는 parsing 외에 Dashboard authorization, matching, switch 또는 response에 사용하지 않는다.

Dashboard `GET /api/repository-inventory`는 strict browser read authorization을 query parsing, Installation과 daemon call보다 먼저 수행하고 모든 query parameter를 거부한다. 응답은 `{repositories:[{name,path,jobCount,dashboardRegistered}],repositoryCount,totalJobCount}`로 제한한다. `dashboardRegistered`는 backend가 각 upstream `root_path`에 대해 기존 platform-aware `Registry.Contains`만 호출해 계산한다. tracked path에 Git inspect/Add/ResolveIdentity를 수행하지 않고, 중복 이름과 upstream order를 보존한다. 이 read는 operation gate, bootstrap repository list, selected repository, registration/switch coordinator, Reviews/Tasks polling, Stats/Insights lifecycle과 결합하지 않는다.

Frontend는 기존 registered repository cards와 Add Local Repository form을 `Repositories` component로 추출해 그대로 유지하고 그 아래에 별도 tracked section을 둔다. component는 inventory 전용 generation과 AbortController를 소유하며 Repositories page mount, explicit Refresh, 성공한 기존 registration 뒤에만 한 번씩 조회한다. polling, SSE, bootstrap/reviews/stats 연계와 selected-repository ownership은 없다. overlap은 latest response만 반영하고 unmount/stale response를 폐기한다. unsupported/offline/error와 post-registration refresh 실패는 tracked section에만 머물며 기존 registry UI와 이미 성공한 registration을 실패로 바꾸지 않는다. Browser는 path equality를 계산하지 않고 backend `dashboardRegistered`만 표시한다.

### Safe repository display-name rename

Repositories v3A는 exact RoboRev v0.64.0의 `repo rename <path-or-name> <new-name>` 중 display name 변경만 노출한다. filesystem path, Git root, Dashboard Registry, selected repository, bootstrap, registration/switch coordinator와 Stats/Insights/Tasks lifecycle은 변경하지 않는다. 기능은 `repositoryInventory`와 분리된 additive `repositoryRename` capability 및 optional rename service에만 놓고 base review `Service`를 확장하지 않는다. Dashboard는 RoboRev DB/SQLite를 직접 열지 않고, daemon에 없는 mutation을 configured executable과 typed argv로만 실행한다. Command의 working directory는 비우며 stale tracked path도 filesystem/Git inspection 없이 metadata identifier로 취급한다.

Browser가 보낸 path는 selector일 뿐 source of truth가 아니다. Preview와 Confirm은 각각 fresh strict `GET /api/repos`에서 byte-exact `root_path`가 정확히 한 행인지 확인하고 command에는 그 저장 문자열만 사용한다. Upstream storage가 path update 0건이면 name fallback을 수행하므로 다른 행의 display name이 target path 문자열과 같으면 fail closed한다. Confirm은 token-bound current name, trimmed new name, binary generation, exact CLI/daemon versions와 health를 다시 확인하며 process 직전에 inventory를 재검증한다. New name은 valid UTF-8, trim 후 nonempty, 최대 128 Unicode code points이고 NUL/CR/LF/Unicode control, unchanged name 및 leading `-`를 거부한다. Leading dash 거부는 Cobra flag parsing이나 추측한 positional terminator에 의존하지 않는 Dashboard 정책이며 builder tests가 exact argv `repo rename <root_path> <new_name>`를 고정한다.

Preview는 process와 operation gate를 사용하지 않고 three-minute cryptographic token을 발급하며 server-side record에 path/current/new name과 full executable/argv/binding/version preflight를 보존한다. Confirm은 기존 ordinary mutation gate 뒤 rename 전용 store에서 token을 single-use로 claim한다. 같은 exact target이 active이면 token을 소비하지 않고 busy를 반환하고, claim 성공은 token 삭제와 active-target 등록을 하나의 mutex 경계에서 수행하므로 동일 token double-submit과 서로 다른 token의 same-path 동시 실행이 모두 process 1회로 제한된다. 다른 path는 기존 ordinary mutation 의미를 유지하며, claim 후 실패는 token을 복구하지 않는다. Token은 job count, Dashboard registration 또는 upstream identity에 bind하지 않는다.

Confirm HTTP handler는 token/target claim과 detached mutation context, optional service 호출 1회 및 typed result의 HTTP 변환만 소유한다. Installation, direct preflight, inventory와 readback을 반복하지 않는다. Adapter operation 하나가 fresh version/health preflight를 정확히 한 번 수행하고 preview의 full preflight와 비교한 뒤, private bounded strict `/api/repos` raw read를 process 직전 한 번과 process 뒤 한 번 수행한다. 따라서 concrete confirm budget은 `version --json` 1회, health 1회, repos 2회, rename process 1회다. Public Repository Inventory는 같은 raw helper 앞에서 기존 독립 version/health/capability preflight를 계속 소유한다.

실행은 shell-free argv, empty CWD, 10초 timeout과 stdout/stderr 각 64 KiB bound를 사용하며 human stdout을 결과로 parse하지 않는다. Process가 시작되지 않았으면 typed error를 공통 mapper로 보내 Binding/Stale/Ambiguous 409, Unsupported/Offline/Unhealthy 503, deadline 504, invalid request 400, unknown 또는 nil-error contract violation 502로 일관되게 응답한다. 시작됐으면 exit code와 무관하게 fresh inventory readback을 수행하고 exact target name이 requested name일 때만 verified success로 판정한다. Readback unavailable, target missing/duplicate, old/third name은 `unverified`이며 retry/rollback하지 않는다. 외부 v0.64 CLI가 Dashboard와 별개로 DB를 여는 check-to-SQL 구간은 transaction/receipt로 잠글 수 없는 잔여 TOCTOU다. exact path/fallback collision 재검증으로 위험을 최소화하지만 절대적인 single-target guarantee로 표현하지 않는다.

Frontend Rename은 tracked inventory row에만 있고 registered card에는 없다. Component mount, inventory, Preview와 Confirm은 독립 generation/controller ownership을 가진다. Availability effect는 inventory request만 invalidate/abort하며 이미 accepted된 Preview/Confirm이나 dialog state를 건드리지 않는다; 실제 component unmount만 모든 child request를 abort한다. Confirm의 guarded `finally`가 single-flight ref를 terminal path마다 해제하고 pending UI는 disabled `Renaming…`을 표시한다. Prepare는 server preview만 만들고 modal은 current/new name, exact path, Jobs, Dashboard registration, executable/argv와 display-name-only 경고를 표시한다. Confirm은 token만 전송한다. Verified success는 modal을 닫고 toast 뒤 independent inventory refresh를 시작하되 refresh 실패가 mutation success를 뒤집지 않는다. `unverified`는 자동 retry/refresh 없이 Refresh만 안내한다. Move/Delete/Merge, polling, Registry mutation과 repository switch는 추가하지 않는다.

### Safe repository path repair

Repositories v3B는 stale RoboRev tracked path를 현재 Dashboard 등록 repository로 복구하는 좁은 path-repair surface다. exact RoboRev v0.64.0에는 daemon move API가 없고 public daemon client도 `GET /api/repos`, `GET /api/repos/resolve`, `POST /api/repos/register`만 제공하므로, Dashboard는 typed shell-free CLI `repo move <source> .`만 사용한다. `.`의 working directory는 fresh `Registry.InspectIdentity`로 검증한 등록 destination의 canonical root이며, Browser는 destination path를 보내거나 고르지 않고 opaque `repositoryIdentity`만 보낸다. CLI와 Dashboard 모두 filesystem, Git root 또는 Dashboard Registry를 이동하지 않는다.

Repair 대상은 RoboRev inventory의 source row 중 stale path가 `Lstat`에서 absent이고 Dashboard Registry에는 등록되지 않은 경우뿐이다. source는 upstream과 동일한 name-or-path resolver를 사용하며, path lookup이 실패해 name fallback으로 넘어갈 수 있는 경우에도 fallback key를 `path.Base`나 추정한 basename으로 바꾸지 않는다. Dashboard의 collision audit는 resolver가 만든 exact post-resolve identifier와 다른 inventory row의 display name을 exact string으로 비교하고, slash/case 정규화나 Windows case-fold를 upstream name lookup에 추론하지 않는다. destination target collision과 source/destination same-path 여부는 Dashboard의 platform-aware path identity로 Preview와 Confirm에서 모두 fail closed한다.

Preview는 process-free이며 source selector, fresh registered destination identity, source stale/unregistered 증거, exact argv와 preflight binding을 cryptographic single-use token에 묶는다. Confirm은 token과 source/destination operation claim을 하나의 atomic 경계에서 소비·예약한다. 이미 사용된 token, 같은 source/destination의 active operation, stale 조건 상실 또는 destination identity drift는 CLI 실행 전에 거부한다. Handler는 browser authorization, token/dual-resource claim, detached operation context, optional service 호출 1회와 typed HTTP mapping만 소유한다. Adapter는 fresh version 1회, health 1회, bounded RoboRev repository read 2회와 process 1회의 예산으로 pre-process 검증·`repo move <source> .` 실행·post-readback을 담당한다.

Process가 시작되지 않은 preprocess failure는 definite typed failure다. Process가 시작된 뒤에는 human stdout과 exit code를 성공 근거로 사용하지 않고 authoritative `/api/repos` readback으로 source가 destination으로 moved 되었는지를 확인한다. readback이 정확히 증명하면 `moved`, readback unavailable·duplicate·old/third row 또는 binding drift로 증명할 수 없으면 `unverified`로 보고한다. `unverified` 이후 자동 retry나 rollback은 없으며, 성공해도 Registry contents, selected repository, registration, repository-switch state는 변경하지 않는다. 기능은 additive `repositoryMove` capability와 optional `RepositoryMoveService` interface로만 노출하고 base review service, inventory read, rename semantics를 확장하지 않는다.

Path repair와 다른 repository-scoped mutator는 하나의 shared resource-ownership domain을 사용한다. Move Confirm은 platform-aware `gitx.RepositoryKey`로 source와 destination을 한 번에 atomic하게 lease하고, 그 lease를 adapter 실행과 authoritative readback이 끝날 때까지 유지한다. Rename의 target도 같은 Gate key domain에 참여한다. Review HEAD와 frozen rerun은 기존 `AcquireReviewLease`를 통해 같은 repository identity domain을 이미 사용하고, Panel Refine, General Fix와 local Configuration도 기존 repository lease를 공유한다. Existing global Fix/Setup/runtime gate semantics는 이 연결로 바뀌지 않는다. 서로 다른 repository key의 resource-scoped operation은 계속 동시에 진행할 수 있다. Move source/destination을 두 번의 순차 claim으로 잠그지 않으며, preview store mutex와 Gate mutex를 동시에 잡지 않는다. Gate가 busy이면 HTTP 409를 반환하고 Move/Rename/Insights의 single-use token은 소비하지 않는다. Guideline Insights도 enqueue가 RoboRev repository row를 생성할 수 있으므로 Confirm 전에 같은 repository lease에 참여한다.

Move의 browser action은 tracked inventory를 읽을 때 filesystem을 선조회하지 않는다. 등록되지 않은 stale row에서 사용자가 명시적으로 path-repair action을 누른 경우에만 lazy `POST /api/repository-moves/eligibility`를 실행한다. 이 endpoint는 fresh inventory에서 source를 unique하게 resolve한 뒤 선택된 source에 대해 한 번의 `SourceAbsent` probe만 수행하며, process 실행·mutation token 발급/소비·destination inspection은 하지 않는다. source가 이미 존재하거나 Dashboard에 등록되어 있으면 `eligible=false`의 명시적 feedback을 반환하고, 그 밖의 preflight 오류도 fail closed한다. inventory endpoint는 모든 tracked path에 대한 eager filesystem probe를 수행하지 않는다. eligibility가 통과한 뒤에도 Preview와 Confirm은 각각 fresh inventory, Registry identity와 source/destination 조건을 authoritative하게 재검증한다.

Path repair는 exact v0.64.0 Installation truth table과 additive `repositoryMove` capability를 따른다: no install(`installed=false`, `repositoryInventory=false`, `repositoryRename=false`, `repositoryMove=false`)은 `runtime-unavailable`, unsupported version(`installed=true`, `repositoryInventory=false`, `repositoryRename=false`, `repositoryMove=false`, `status.running=false`)은 `unsupported`, exact v0.64.0 offline(`installed=true`, `repositoryInventory=true`, `repositoryRename=true`, `repositoryMove=true`, `status.running=false`)은 `runtime-unavailable`, exact v0.64.0 online(`installed=true`, `repositoryInventory=true`, `repositoryRename=true`, `repositoryMove=true`, `status.running=true`)은 `available`이다. Installed + daemon-looking defensive fixture에서 `installed=true`, `repositoryInventory=true`, `repositoryRename=true`, `repositoryMove=false`, `status.running=true`이면 `unsupported`가 우선한다. 이 truth table은 frontend fixture와 backend capability tests에서 고정한다.

### Safe repository merge

Repositories v3C는 일반적인 repository merge 도구가 아니라, filesystem에서 사라진 stale RoboRev source row를 현재 Dashboard에 등록되어 있고 RoboRev에도 이미 tracked된 target row로 합치는 duplicate-recovery surface다. exact RoboRev v0.64.0 audit 결과 더 안전한 daemon mutation API는 없고, 유일한 upstream mutation은 typed CLI `repo merge --yes <source> <target>`이다. 두 identifier는 `resolveRepoIdentifier`를 거친 뒤 storage의 `FindRepo` path-first/name-fallback semantics를 사용한다. Dashboard는 사람이 보는 stdout(`Merged N jobs ...`)이나 JSON receipt를 계약으로 사용하지 않는다.

Upstream `MergeRepos(sourceID, targetID)`는 dedicated transaction에서 `BEGIN IMMEDIATE`를 수행하고, commit 전 오류에는 rollback한다. source commits는 target으로 이동하고, source `review_jobs`는 target으로 reassociate되며, `agent_hook_snoozes`는 target conflict resolution을 거쳐 consolidate된다. 마지막에는 source repository row가 삭제되고 target row의 name/path는 유지된다. 이 operation은 filesystem이나 Git root를 이동하지 않고 Dashboard Registry를 만지지 않는다. Source와 target이 같은 row인 경우 upstream은 no-op이지만 Dashboard는 Preview 전에 명시적으로 거부한다. Source job이 0개여도 upstream은 source row를 삭제할 수 있으므로 Dashboard는 이를 Delete 우회로 취급해 지원하지 않는다.

Safe Merge의 policy는 fresh inventory에서 정확히 한 source row, Dashboard-unregistered source, `Lstat` absent path와 `jobCount > 0`을 요구한다. target은 Browser가 보낸 path가 아니라 opaque `repositoryIdentity`로 선택하며, backend가 fresh `Registry.InspectIdentity`로 authorization과 canonical Git root를 확인한다. 그 canonical root가 fresh RoboRev inventory에도 정확히 하나의 tracked row로 나타나야 하고, missing/duplicate/ambiguous target은 fail closed한다. Upstream `identity`는 matching, authorization 또는 browser response에 사용하지 않는다. Source path와 target identity/path/name/jobCount, exact command, resolver fallback keys, binary binding, CLI/daemon versions를 token-bound preflight에 고정하며 source 또는 target count가 Confirm에서 drift하면 process 0인 stale 409다.

Queued/running source jobs는 worker snapshot이 source path를 계속 사용할 수 있고, merge가 row를 target으로 바꾼 뒤에도 이미 실행 중인 worker가 stale source path로 계속 진행할 수 있으므로 하나라도 있으면 Merge를 거부한다. 이 검사는 parent-only `/api/jobs`의 기본 필터를 전체 review_jobs 증거로 오해하지 않는다. Bounded typed streaming으로 source의 non-member parent rows를 끝까지 확인하고, 각 panel summary의 member/parent activity와 represented counts를 대조하며, fresh inventory의 source `jobCount`가 그 bounded representation과 일치하는지 검증한다. panel member가 parent summary로 표현되지 않거나 페이지/stream bound, malformed row, count mismatch, unknown status 또는 any active queued/running row가 있으면 active-job state를 증명할 수 없으므로 fail closed한다. 이 마지막 bounded `/api/jobs` 감사는 point-in-time 검사일 뿐이다. exact v0.64 upstream에는 active-job precondition을 merge transaction과 원자적으로 묶는 API가 없고, Dashboard Gate도 임의의 외부 RoboRev producer/worker를 직렬화할 수 없으므로, 감사 직후 외부 enqueue가 발생하는 check-to-`repo merge` TOCTOU는 제거할 수 없다. 따라서 정책은 새 외부 enqueue까지 없다고 증명하는 것이 아니라 감사 시점의 active state에 대해 fail closed하는 것으로 한정한다. Target active jobs는 `MergeRepos`가 target-owned rows를 mutate하지 않는 upstream contract로 확인되므로 별도 target-inactivity 조건으로 넓히지 않지만, target resource는 shared lease로 보호한다.

Preview는 process 없이 fresh version/health/inventory, source stale/unregistered/job count, complete active-job safety audit, target registry/tracked resolution, fallback ambiguity와 exact command를 계산해 cryptographic single-use token을 발급한다. Confirm body는 `{token}` 하나만 허용한다. Handler의 lock order는 token을 먼저 peek하고 store mutex를 놓은 뒤 source+target 두 resource를 기존 shared Gate에서 atomic하게 lease하고, 다시 store mutex를 잡아 token을 claim하는 순서다. Preview-store mutex와 Gate mutex를 동시에 hold하지 않으며, Gate busy는 409이고 token을 소비하지 않는다. Rename, Move, Review enqueue/rerun, Fix, Refine, local Configuration 등 기존 repository lease consumer와 같은 key namespace를 사용하고 서로 다른 repository는 계속 concurrent하다.

Adapter는 fresh preflight를 다시 수행한 뒤 exact `repo merge --yes <source-exact-path> <target-exact-path>`를 empty CWD의 shell-free typed process로 한 번 실행한다. Confirm budget은 version 1회, health 1회, bounded inventory/active-job evidence와 target validation, process 1회, post-readback 1회이며 handler가 이를 중복하지 않는다. Process가 시작되지 않으면 definite typed failure다. 시작된 뒤에는 exit code/stdout을 신뢰하지 않고 readback으로만 판단한다. 최소 verified condition은 source row absent, target row unique, target name/path 보존, target `jobCount >= S + T`다. `>=`는 Dashboard 밖에서 target에 새 job이 생길 수 있기 때문이다. Readback이 부족하거나 source가 남거나 target이 missing/duplicate/renamed거나 count가 부족하면 `unverified`로 보고하며 자동 retry/rollback하지 않는다. Success는 source RoboRev tracking entry 삭제와 consolidated metadata를 확인하지만 Registry, selected repository, registration/switch state, filesystem 또는 Git은 변경하지 않는다.

`repositoryMerge`는 exact supported v0.64.0에서만 true인 additive capability와 optional `RepositoryMergeService`로 노출한다. Capability truth table은 existing runtime model을 따른다: no install은 `runtime-unavailable`; unsupported version의 inventory/rename/move/merge capability가 false인 fixture는 `unsupported`; exact v0.64 offline은 `runtime-unavailable`; exact v0.64 online은 `available`; installed daemon-looking mixed fixture는 `unsupported` 우선이다.

### Repository deletion blocked

Repositories v3D Safe Delete는 exact RoboRev v0.64.0에서 **BLOCKED**다. Non-cascade `DeleteRepo`는 transaction 안에서 `review_jobs` count만 재검사하므로 `jobCount == 0`이 commit 또는 legacy commit response 부재를 증명하지 않는다. v0.64.0은 job 없이 commit과 legacy response가 존재하는 상태를 허용하며, `commits.repo_id` foreign key에는 delete cascade가 없다. 따라서 connection-local SQLite foreign-key enforcement가 꺼져 있으면 repository row 삭제가 commit/response orphan을 만들 수 있고, 켜져 있으면 delete 자체가 foreign-key violation으로 실패할 수 있다. 어느 결과도 Dashboard가 보장해야 하는 tracking-only cleanup 계약이 아니다.

`repo delete --cascade`는 responses, reviews, `review_jobs`, commits와 repository row까지 삭제할 수 있으므로 Dashboard에서 영구적으로 노출하지 않는다. 더 안전한 upstream contract 또는 machine-readable mutation API가 제공되기 전까지 repository delete capability, UI, Preview/Confirm API와 typed delete process를 추가하지 않는다. Exact v0.64.0에서 Rename, Move와 Merge는 지원 완료지만 Delete는 planned가 아닌 unsupported/blocked 상태다.

## 확장 원칙

각 RoboRev 기능은 service method, typed request, command builder, capability, HTTP route, confirmation 정책과 테스트를 함께 추가한다. CLI help에서 확인되지 않은 flag를 추측해 만들지 않는다. 중요한 변경은 이 문서와 coverage matrix를 함께 갱신한다.

### Skills Readiness v1

Skills Readiness is an additive, global, read-only `GET /api/skills/readiness` surface. Its only production RoboRev transport is the exact v0.64.0 root `skills` command, which delegates to upstream `ListSkills()` and `Status()`. This path reads agent configuration and embedded skill content, has no daemon lifecycle, LLM, network, skill-file write or legacy `RemoveAll` behavior. `skills install` and `skills update` are never used as status probes and there is no mutation, `--path`, content viewer or custom path surface in this checkpoint.

The backend gates the request on strict browser read authorization, an empty query, a fresh Dashboard-owned exact v0.64.0 binary/version binding, one bounded `skills` process with exact argv `['skills']`, strict human-output parsing and a final binding revalidation. Shell execution, arbitrary browser argv, full environment inheritance and raw upstream output are not allowed. Only the minimal Windows home/config variables required by upstream resolution (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `GROK_HOME`, `HOME`, `USERPROFILE`) are supplied; Git variables, credentials, unrelated `ROBOREV_*` values and arbitrary environment entries are excluded. Bounded stdout, empty stderr, zero exit and valid UTF-8 are required; truncation, timeout, nonzero exit, stderr, invalid UTF-8 or binding drift fail closed.

The parser is version-gated and uses an exact v0.64.0 embedded-catalog allowlist. It verifies each expected skill, supported-agent membership, exact human agent label and invocation prefix (`$` for Codex, `/` for Claude Code, Grok Build and Factory Droid), badge (`installed`, `outdated`, `not installed`, `no agent`), duplicate/missing rows and structural completeness. Unknown skills/agents/statuses, wrong prefixes/names, malformed or status-like extra lines and truncated output are rejected. Codex `agents/openai.yaml` content is included in upstream comparison, so an upstream `outdated` result remains `outdated`; Dashboard does not downgrade it. Descriptions are parser-only data and never cross into the browser.

The browser DTO contains only exact v0.64.0 `version` and four fixed-order agent rows (`codex`, `claude`, `grok`, `droid`) with aggregate status and nonnegative counts. Each total is the fixed exact catalog total of 10. `current` requires all 10 current; `needs-install-update` requires counts summing to 10 with at least one outdated or missing skill; `config-unavailable` requires zero current/outdated/missing and means only that the agent configuration directory was not detected, not that the agent executable is absent. Config/home/skill paths, `SKILL.md` or `agents/openai.yaml` paths, binary path, executable, command/argv, raw stdout/stderr, descriptions, skill contents and arbitrary errors are excluded.

The React card owns a separate module-scoped settled/in-flight resource. Initial surface entry and React StrictMode share one GET; explicit Refresh adds one fresh GET; locale changes and repository-key remounts add zero. No polling or SSE is used. Generation/abort guards discard superseded refresh responses, and unmounted components ignore late updates. In the Skills Readiness v1 read-only baseline, Agents & Setup exposes only the Refresh control and no mutation, open-file or content controls; the v2 mutation surface below is deliberately separate from this read resource. Upstream `skills install` calls `installSkills` and `removeLegacySkills`, loops supported agents, writes multiple skill trees and can `RemoveAll` the legacy `roborev-address` directory; `skills update` likewise visits existing/current or legacy installations, calls `installAgent` and can remove that legacy directory. Although `skills install --path <directory> --agent <variant>` accepts an arbitrary destination, it is never browser-supplied.

### Skills Management v2

Skills Management v2 adds a narrow mutation surface to the Skills Readiness card. Only an agent whose fresh readiness row is `needs-install-update` can expose Install / Update, and one operation changes exactly one of `codex`, `claude`, `grok` or `droid`. Current and config-unavailable rows have no CTA. There is no Install All, Update All, Remove, Uninstall, custom path, folder browser or legacy-cleanup action.

The exact v0.64.0 audit is authoritative (official tag `v0.64.0` source audit). The root `roborev skills` command remains read-only. Dashboard never launches broad `roborev skills install` without `--path` and never launches `roborev skills update`, because those upstream paths can visit multiple configured agents and can remove the legacy tree. The sole production mutation command is a typed, shell-free process with exactly one selected agent and exactly these arguments: `skills install --path <server-derived-absolute-agent-skills-directory> --agent <agent>`. The browser sends only `{agent}` for preview and only `{token}` for execution; it cannot supply a path, config directory, home, binary, command, argv, scope or timeout. No shell, `cmd.exe` or PowerShell wrapper is involved.

The server reproduces the v0.64.0 target resolver. A nonempty `CLAUDE_CONFIG_DIR`, `CODEX_HOME` or `GROK_HOME` is selected verbatim for the corresponding agent; otherwise the resolver uses `os.UserHomeDir()` plus `.claude`, `.codex` or `.grok`. Droid uses a nonempty `HOME` verbatim, otherwise `os.UserHomeDir()`, and appends `.factory`. Each config root then appends `skills`. The selected value is not trimmed before selection, but the final config and skills paths must be absolute and canonical. Relative overrides are blocked; Dashboard never turns a cwd-dependent configuration into a hidden write. The existing config root must already exist as a safe, canonical, non-symlink/non-reparse directory. Config-unavailable agents therefore remain blocked and Dashboard does not create their configuration tree.

The write-set comes from one shared v0.64.0 embedded manifest, also used by Skills Readiness. Every selected agent plans the ten bundled `SKILL.md` files (`roborev-design-review`, `roborev-design-review-branch`, `roborev-fix`, `roborev-lookahead-review`, `roborev-lookahead-review-branch`, `roborev-refine`, `roborev-respond`, `roborev-review`, `roborev-review-branch` and `roborev-snooze`). Codex additionally plans each bundled `agents/openai.yaml`. The Dashboard checks the complete manifest-derived tree before preview and binds it to the token: config-root identity, skills target, existing directory/file type and identity/fingerprint, safe missing-ancestor witnesses, the selected resolver semantics, legacy absence, exact version/binary binding and readiness counts. Existing managed files may be overwritten by the bundled content, including a stale user-edited `SKILL.md` or Codex policy. Unrelated skill directories and unknown files inside managed directories are not in the write-set and remain untouched; the exact upstream install contract does not remove them.

The legacy path `<skillsDir>\roborev-address` is a hard safety boundary. Because v0.64.0's `removeLegacySkills` unconditionally calls recursive `RemoveAll`, any legacy file, directory, symlink or reparse point blocks both preview and execute. Dashboard does not authorize or perform that cleanup and never exposes the actual legacy path. The absence proof is included in the tree snapshot. All Dashboard-controlled slow readiness and binding subprocesses complete first; a final complete target/tree/legacy guard then runs immediately before the mutation process launch, with no Dashboard-controlled subprocess between that guard and launch. There is an honest residual race: without an upstream `--no-legacy-cleanup` mode, an external actor can create `roborev-address` after Dashboard's final filesystem check and before upstream cleanup; filesystem atomicity against an external writer is not guaranteed.

Preview performs strict mutation authorization, empty-query and exact-body validation, agent allowlisting, a fresh exact Skills Readiness probe, `needs-install-update` eligibility, server-side target resolution, existing-root proof, full tree safety snapshot and legacy absence verification before creating a short-lived single-use token. The sanitized DTO contains only the selected agent, semantic action/summary, the fixed display command with `roborev`, `skills install`, `--path <agent-skills-directory>` and `--agent <agent>`, plus expiry. Actual path, executable, content, environment and raw process output remain server-side. The preview is display-only and is not execution authority.

Execute claims the token once, revalidates the exact binary/version binding, acquires the same global exclusive `operation.Gate.AcquireFix()` slot used by Agent Hook Management, re-resolves the server target, compares the target and complete tree snapshot, rechecks legacy absence and fresh readiness, and performs a final fresh target/tree/legacy guard immediately after the last binding probe and immediately before one typed CLI launch. No Dashboard-controlled subprocess or other slow probe occurs between that final guard and launch. No repository identity or repository lease is involved. Any stale target, tree, binding, legacy path, readiness or gate state blocks before process start. A started process always gets a detached, bounded post-readback: fresh Skills Readiness, unchanged target resolution, safe post-state and binding verification. Request cancellation or browser disconnect cannot skip that readback.

Results are honest and typed. `verified-success` requires a started process and a safe post-state whose selected agent is current; a CLI error may coexist with verified success and is retained as `cli-failed`. `partial` requires a started process, a safe post-state that is still needs-install-update and measurable improvement from the token snapshot. `failed-unverified` covers not-started execution, unavailable readback, drift, unsafe post-state or no improvement. A process that never started never receives credit for an external actor making the tree current. There is no automatic retry or rollback because upstream writes bundled files sequentially and an error can follow earlier writes. Completion reloads the independent Skills Readiness resource once; there is no polling or SSE/cache coupling. Review Export remains BLOCKED on exact v0.64.0.
## Guideline Insights v1 (2026-08-23)

Guideline Insights is an isolated optional `roborev.InsightsService`; the base review `Service`, Stats Summary/Cost lifecycle, Setup health meanings, operation gate, Tasks history and repository-switch coordinator are unchanged. Only exact v0.64.0 enables the additive `guidelineInsights` capability.

The selected registered repository is inspected freshly for Preview and Confirm. Browser input is limited to `repositoryIdentity`, `7d|30d|90d` (default 30d), and `all|current`; current scope resolves the authoritative branch and rejects explicit detached-HEAD state, empty and `HEAD`, while an attached branch literally named `detached` remains valid. The backend builds the exact shell-free argv `insights --repo <repo> [--branch <branch>] --since <window> --json`, using RoboRev's configured agent/model/reasoning defaults and never adding `--wait`, `--agent`, `--model`, `--reasoning`, `--agentic`, or `--yolo`.

Preview creates a cryptographically random, three-minute, single-use server token bound to identity, canonical path, scope/window/branch, binary binding generation, and exact CLI/daemon versions. Confirm re-inspects and re-preflights immediately before one launch, atomically consumes the token, and uses a selected-repository lease through the launch boundary. A non-2xx Confirm response is a definite pre-process failure; an accepted HTTP 202 `unverified` response, a missing network response, or a malformed successful response is conservatively treated as possibly queued. Any error after process entry—including timeout, cancellation, truncation, malformed receipt, or binding drift—is reported as `unverified`; the token is never restored and no automatic retry exists. Receipt parsing is strict and bounded (64 KiB): success requires positive JS-safe `job_id`, bounded nonempty `agent`, and RFC3339 `since`; skip is a normal `{skipped:true,reason,since}` outcome.

Status/result reads require strict browser read authorization, one repository identity, registered ownership, matching `job_type=insights`, and the allowlisted queued/running/done/failed/canceled statuses. Queued/running responses contain no prompt/output. Done results return only bounded Markdown. The React `GuidelineInsights` component owns four independent lifetimes: Preview/Confirm interaction, status polling, completed-result loading, and the repository-scope epoch above them. Poll/result cleanup cannot invalidate a new interaction; only a new Prepare or repository boundary may explicitly retire older tracking. Polling stops at terminal status, while done-result loading and same-job GET-only recovery have a separate controller/generation. Repository identity changes and authoritative switches invalidate every child lifetime and discard late responses. The component never launches on mount, Stats refresh, scope/locale/suspension changes, or background events. Recommendations are read-only and have no Apply/Save/config mutation path. The approved narrow shared-policy exception hides generic Cancel/Rerun buttons for Insights in ReviewDetail and rejects generic backend rerun for `job_type=insights`; generic cancel backend policy is unchanged.

### Lazy Prompt / Raw Log transport hardening (2026-08-24)

ReviewDetail Prompt and Log are explicit, daemon-only lazy reads against the exact v0.64.0 machine-facing HTTP API. The Dashboard no longer invokes `show --job --prompt` or `log --raw`, and these reads never start or restart a daemon or acquire the mutation Gate. Each read performs one bounded version/reachability preflight, requires matching CLI/daemon v0.64.0 (reachable `healthy:false` remains readable), and keeps ownership plus content on that same binding. Health, owner, and content HTTP calls shallow-copy the configured client with redirects disabled; non-200 responses are rejected before their bodies are consumed. Binding generation is checked before the owner/content boundary and after complete validation; drift returns a typed failure without stale content.

Completed prompts use `/api/review?job_id=...`; only a 404 permits the strict queued/running `/api/jobs?id=...&limit=1&omit_prompt=true` fallback. JSON is typed, single-value, content-type checked, identity checked and bounded at 8 MiB with no partial success; unknown full-review fields are tolerated and an empty completed prompt is valid. Logs use `/api/job/log?job_id=...&offset=0`, require `application/x-ndjson`, a known `X-Job-Status`, canonical nonnegative int64 `X-Log-Offset` equal to the body byte length, valid UTF-8 and the same 8 MiB+1 bound. Empty running logs at offset zero are valid.

Strict browser authorization and positive-ID parsing happen first. Lazy ownership does not assume `omit_prompt=true` is metadata-only: exact v0.64.0 keeps stored prompts on queued/running rows. The adapter therefore requests the target with `/api/jobs?id=...&limit=1&omit_prompt=true`, then reads only a 128-byte, byte-at-a-time prefix whose canonical first row is `id` followed by `repo_id`; it stops immediately after the `repo_id` delimiter and never full-reads or JSON-decodes the row. It compares that repo ID with same-repo witness prefixes from a frozen, sorted `FreshRegisteredPathsWithStatus` membership snapshot. Registry inspection uses a Registry-owned hard maximum of two detached probe goroutines, a 3-second per-root cancellation deadline and a 6-second caller phase bound; a blocked OS probe holds its slot until `Inspect` returns, so capacity exhaustion is temporary unavailable rather than an unbounded request leak. Admission rotates deterministically across the frozen roots and completed roots remain usable, while unfinished, unlaunched, or late probes mark the snapshot incomplete; when capacity recovers, retries make eventual progress, but permanently blocked slots degrade to 503. Each lazy operation consumes one client-scoped daemon-witness cursor ticket, so its first witness order rotates across sorted roots without two-proof double advancement. The final proof retries the matched frozen path first, then the same frozen remainder, so a slow lexical prefix cannot delay a known owner; a preferred mismatch, 404, or local witness error safely falls through the remainder. This also authorizes panel members through their atomic same-repository synthesis witness. Witnesses are checked sequentially under one 15-second operation deadline, so the authorization set cannot expand mid-request. Empty paths fail immediately; malformed, oversized, transport, and non-2xx witness-local failures (except 404, a valid negative) are recorded while later witnesses continue, with cancellation/deadline or binding drift aborting immediately. Only a full 200 with a parsed matching `repo_id` authorizes; if none matches, the first witness error is returned, otherwise authorization is forbidden. If a completed witness authorizes while registry inspection is incomplete, the read still succeeds; an incomplete no-match is reported as temporary witness unavailability rather than a false 403. Error bodies and redirect responses are not consumed or followed, and foreign prompt/log bytes are not read before owning-repository authorization. Only after a witness match does the adapter call `/api/review` or `/api/job/log`; the same frozen ownership proof runs again after content retrieval before returning bytes to the browser. Lazy content is exposed only through the optional `AuthorizedPrompt`/`AuthorizedLog` surface; unowned prompt/log methods and CLI args are absent. List polling never carries prompt/log bodies.

### CI Workflow Preview v1

CI Workflow Preview v1 is a repository-scoped, read-only preview for one selected registered Dashboard repository. It is deliberately separate from repository initialization and from any future workflow write action. The only browser input is the opaque `repositoryIdentity`; the UI does not accept a path, output filename, agent, version, force flag or arbitrary command. The endpoint is an explicit Generate action behind strict same-origin/CSRF authorization and exact `POST`/body validation. It does not poll, use SSE, start a daemon, invoke an LLM, access RoboRev storage, make a network request, register a repository or mutate repository state; the selected repository is still freshly inspected read-only for canonical authorization.

The exact upstream v0.64.0 audit is authoritative. Root `roborev init` can create the global data directory and default global configuration, optionally create repository `.roborev.toml`, modify `.gitignore` for the snapshot directory, set `core.hooksPath`, create hook directories, install `post-commit`/`post-rewrite` hooks, start the daemon and register the repository. Consequently root `roborev init` remains P/planned and has production occurrence 0 in this checkpoint; it is never a preview transport or a B capability. The `init gh-action` child command is the only generation transport and is invoked from a fresh canonical repository cwd with exact arguments equivalent to `init gh-action --output <server-private-temp>\roborev.yml --roborev-version 0.64.0`. Dashboard does not add `--agent`, `--force`, a shell wrapper or any other flag. The root `init` occurrence must remain zero in the command builder and production path.

Upstream `init gh-action` resolves configuration through `LoadGlobal` and `LoadRepoConfig`, but its resolver discards those load errors and can fall back. Before generation, Dashboard performs a safe typed effective-configuration preflight through the normal upstream resolution path and fails closed on malformed or invalid configuration. This is validation only: Dashboard does not implement a second large config parser, write config, or expose config rows, origins, paths or errors. The environment supplied to both preflight and generation keeps only the runtime/home/location variables required for that normal resolution and strips Git routing, credentials, API keys and unrelated `ROBOREV_*` values.

The process binding is fresh before generation and freshly revalidated afterward. The executable remains an internal canonical regular-file binding; a missing, non-regular, symlink/reparse, unsupported-version, identity or generation drift fails closed. The server creates an unpredictable private OS temporary directory outside the selected repository, verifies that the output is absent, and owns cleanup on success, error and cancellation. Only the fixed private output is read after the process. The read is bounded to 256 KiB, requires a stable regular non-symlink/non-reparse file, valid UTF-8 and no NUL/control characters, and returns the exact bytes plus SHA-256. Output parent creation and the generated file are confined to that private temporary directory; no repository file/directory/config/hook/Git change, daemon start, registration or other persistent write is allowed. Upstream `WriteWorkflow` itself creates the supplied output parent and writes the file, rejects an existing file without `--force`, and can overwrite with `--force`; Dashboard always uses an absent private output and `--force` occurrence 0.

The browser DTO contains only `version: "v0.64.0"`, the selected repository identity, fixed target `.github/workflows/roborev.yml` and generated workflow `content`/`sha256`. `targetStatus` is intentionally omitted in v1, so the endpoint never reads or reports the repository's existing target. Actual temporary paths, canonical repository path, executable/binary path, command/argv, cwd, environment, process identifiers, raw stdout/stderr and upstream errors do not cross the server boundary. Secret references rendered by the upstream template are allowed in the preview; actual secret values are never read, stored or returned. The generated template is pinned to RoboRev v0.64.0, but its agent installer steps may use npm `@latest`, unpinned Droid `pip` installation and the Grok external `curl -fsSL https://x.ai/cli/install.sh | bash` installer; the UI must show this supply-chain warning rather than imply that every action is pinned.

Agents & Setup adds a compact Generate-only card near repository-scoped Git Hooks. Initial entry makes no request. One synchronous guard permits one POST per click; repository changes clear the result, do not fetch automatically and discard late responses from the old identity. Locale changes are local-only and may preserve the current result. Unmount ignores late completion. The card displays the fixed target, v0.64.0, supply-chain warning, plain-text YAML and Copy; it has no write CTA, force option, custom output, custom agent/version, polling or SSE. A later checkpoint may add an explicit, separately named repository write flow with its own preview/confirmation, target safety proof and authoritative readback; v1 does not write `.github/workflows/roborev.yml`.

The final pre-launch ordering remains Skills Readiness/Management before this future CI write checkpoint, and Review Export remains **BLOCKED** on exact v0.64.0. CI preview does not change those capability or lifecycle contracts.

All Dashboard-controlled configuration validation and exact-binary binding subprocesses complete before a final complete server-owned temporary-root/output binding guard. Immediately before launch, that guard recaptures the private temp root's identity and path chain, proves the exact output is absent, and binds the output's direct parent identity to the validated private temp child. Any guard failure is sanitized, generation is not launched, and cleanup remains limited to that validated private temp child. After a successful guard, no Dashboard-controlled operation—subprocess, path probe, or other slow work—occurs before the `init gh-action` process launch.

This does not claim perfect filesystem atomicity. Exact upstream `WriteWorkflow` accepts an output pathname rather than an already-open safe file handle, so an external same-user actor can still race between the final guard and upstream's open/write; that residual is outside Dashboard's control and is not represented as an atomic guarantee.

### CI Workflow Management v2

CI Workflow Management v2 extends the v1 preview with one explicit, create-only repository mutation. Preview generation remains the v1 `init gh-action` process in a private temporary directory; the Management execute path never invokes `roborev init`, `init gh-action`, `config list`, `version`, a daemon lifecycle command or any other RoboRev subprocess. The browser submits only the opaque `repositoryIdentity` to preview and only an opaque single-use write token to execute. It never submits workflow content, digest, path, version, agent or force/overwrite options.

Preview still returns the exact generated bytes and SHA-256, but it also performs a read-only eligibility check for the fixed target `.github/workflows/roborev.yml`. The target absolute path is derived only on the server from the freshly canonical selected registered repository root. The sanitized write status is one of `available`, `exists`, `unsafe`, `ignored` or `dirty`; only `available` produces a token. Existing, ignored, unsafe or dirty targets remain previewable when generation succeeds, but fail closed for write. Existing workflow content is never merged, backed up, replaced or overwritten. This is deliberate: v2 has no semantic merge, byte-diff approval, backup, atomic replacement or symlink-safe replacement contract for user-owned YAML.

The server-side token store is bounded in both lifetime and cardinality. A pending token expires after three minutes, is removed on expiry and can be claimed only once. Its binding includes the opaque repository identity, canonical root and root identity, full HEAD, current branch, clean-tree baseline, fixed relative and server-derived absolute target, `.github` and `workflows` directory snapshots, nearest safe ancestor witnesses, target absence, `ignored=false`, the exact preview bytes and digest, the pinned RoboRev v0.64.0 version and expiry. The browser never receives this private binding. A preview token is execution authority only after all of these facts are freshly checked again.

Execute uses the existing shared global mutation Gate and selected repository lease; it does not create a parallel filesystem-mutation domain that could race Skills Management, Agent Hook Management, Git Hook Management or other repository mutations. After strict same-origin/CSRF authorization, empty-query and exact-body validation, token claim and serialization, the backend re-resolves the selected registration and checks the root identity, branch, full HEAD, clean working tree, fixed target, `.github`/`workflows` snapshots, target absence and non-ignored state. Any drift consumes the token, returns a sanitized stale/conflict result and performs zero file creation.

When directories are missing, the backend creates only the fixed `.github` and then `workflows` components. Each component is checked against the expected root/ancestor identity, rejected if it is a symlink/reparse or non-directory, created with portable mode 0755 and immediately revalidated by fresh identity. Before opening the workflow file, a final parent guard proves the canonical `.github/workflows` path and identity, its containment within the selected root and absence of the target. No Dashboard-controlled slow operation or subprocess runs between this guard and the file create.

The target is created with an atomic no-replace primitive (`O_EXCL`/Windows create-new equivalent) and mode 0644. It is never written with an overwrite-capable `WriteFile` call, and no `MkdirAll`, `--force`, remove, replacement, Git add, commit or push is used. The bytes come only from the token-bound preview; the server does not parse, reformat, normalize newlines, translate or rewrite YAML. After write and close (and sync where the platform convention supports it), a bounded stable readback requires the fixed regular non-symlink/non-reparse target, exact bytes and digest. A final repository read confirms unchanged repository identity/root, branch and full HEAD; the expected working-tree dirty state from the created file is not treated as an error.

The absolute repository/target paths, binary/temp paths, directory identities, environment, process details, raw output and filesystem error details remain private to the server. Browser responses contain only fixed relative target text, opaque identifiers/tokens and sanitized status/result codes.

Results are `verified-created` only when the target readback is exact and the repository identity/root/branch/HEAD checks still match, or `failed-unverified` when creation, parent/file identity, write, readback, digest or repository checks cannot establish that fact. A write error may still be reported as verified-created with a sanitized warning if the complete exact target is subsequently proven. Sequential directory creation can leave newly created empty directories, and a failed write can leave a partial file; the Dashboard does not claim zero mutation, does not automatically retry and does not roll back. Browser disconnect after mutation begins cannot skip detached bounded verification, and HTTP delivery failure is kept separate from the filesystem result.

The UI reuses the v1 card. An available preview exposes `Create Workflow`, which opens a confirmation dialog without a request; only confirmation performs one execute POST, with cancel and double-confirm guards. Existing, ignored, dirty and unsafe statuses have no create CTA and show localized fail-closed explanations. Success invalidates the token and removes the CTA, saying to review the workflow and commit/push with Git; failure asks the user to inspect the repository before retrying. Repository switches clear preview, token, dialog and result and discard stale work without auto-preview or auto-execute; locale changes are local-only; polling and SSE remain absent. The supply-chain warning remains because the YAML pins RoboRev but may use npm `@latest`, unpinned Droid pip and the external Grok installer.

The Management adapter deliberately does not call the exact upstream direct repository writer. The v0.64.0 `WriteWorkflow` implementation uses `Stat`, `MkdirAll` and `WriteFile`; existing files fail without force and `force=true` can overwrite. That broader pathname writer is retained as a P/not-used-by-Dashboard reference. Management v2 instead owns the narrower fixed-target, create-only and readback contract. It is not a perfect repository-wide transaction: another process may change unrelated files during the operation, and an external same-user actor may still race after the final parent guard because the no-replace open is performed by the operating system on a pathname. `verified-created` therefore proves only the expected target bytes and unchanged root/branch/HEAD, never that only this file changed.

Skills Readiness/Management remains ahead of the CI write checkpoint in the final pre-launch ordering, and Review Export remains **BLOCKED** on exact v0.64.0. Tests use deterministic fake filesystem, Git and process services only; actual workflow creation, RoboRev execution, daemon/LLM jobs and external RoboRev review remain excluded.

### CI Workflow Drift v3

CI Workflow Drift v3 is an additive, read-only comparison on the existing CI Workflow Preview / Management card. It runs only during an explicit preview request, against the fixed server-derived target `.github/workflows/roborev.yml` beneath the selected canonical repository root. The browser cannot choose a path, workflow, version, or comparison target, and the server never scans or enumerates the workflow directory.

After the one exact v0.64.0 private-temporary `init gh-action` generation, the server determines the existing-target write status and reuses those generated bytes for comparison. Only `write.status=exists` invokes the management service's `CompareExisting`; `available`, `dirty`, `ignored` and `unsafe` responses omit `existing`. `existing` contains exactly one allowlisted enum: `exact-match`, `different` or `unavailable`. Existing workflow content, path, digest, diff and filesystem errors never cross the HTTP boundary, and no additional generation, Git scan, RoboRev process, filesystem mutation or write authority is introduced.

The comparison validates the private identity-bound Plan topology and revalidates the root, `.github` and `workflows` directory snapshots immediately before and after exactly one `pathsafety.ReadStableFile` call for the fixed target. The read is bounded to 256 KiB and proves a regular, non-symlink/non-reparse file, open-handle identity and stable pre/post path-chain identity. The returned target snapshot must equal the Plan snapshot. Any invalid Plan, cancellation, read error, oversize, identity/fingerprint drift, ancestor drift or unstable read is `unavailable`; absent and unsafe targets return before opening the target. A safe complete read is classified authoritatively only with raw `bytes.Equal` against the already-generated preview bytes. There is no YAML parsing, key normalization, comment stripping, whitespace or line-ending normalization, semantic equivalence or reserialization: LF/CRLF, trailing-newline and comment differences are `different`.

`different` is a neutral byte fact, not `outdated`, `broken`, `invalid` or `unsafe`. The UI adds only the localized comparison sentence beside the existing-workflow message and keeps the generated YAML and Copy control. It exposes no diff/view-existing/update/overwrite/replace/sync/reset CTA. Existing-target status continues to suppress the create token, and Management v2's create-only O_EXCL contract, stale guards, post-readback and no-overwrite behavior remain unchanged. Review Export remains BLOCKED, and Skills Readiness/Management and Agent Hook Management guards are unaffected.
